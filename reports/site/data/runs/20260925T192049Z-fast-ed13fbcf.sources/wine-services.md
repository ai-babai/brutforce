# Поиск и рекомендации — контракт для Романа

Статус: согласована граница, версия HTTP-контракта 1.0.0. Задача BE-032.
Машинный источник: [wine-services.openapi.json](wine-services.openapi.json).
Вход агенту Романа: [ROMAN-SERVICES.md](../docs/agent-guide/ROMAN-SERVICES.md).

## Назначение и границы

Пользователь ищет вино по фото/названию, выбирает карточку, затем может открыть похожее вино.
Это две задачи: идентификация и рекомендации альтернатив. Список кандидатов распознавания
не выдаём за персональную рекомендацию. Профиль вкуса и персонализация пока вне объёма.

```text
Браузер → Go API приложения ─┬→ Search service (фото/текст)
                            ├→ Recommendation service (ID вина)
                            └→ каталог PostgreSQL (содержимое карточек)
```

Производитель внутренних HTTP API — реализация Романа или эталонная заглушка.
Потребитель — наш Go API. Фронтенд не знает адресов/секретов внутренних сервисов.
SEARCH_SERVICE_URL и RECOMMENDATION_SERVICE_URL независимы: разрешены один процесс
или два сервиса. Делить фото/текст на отдельные процессы пока не требуется.
Общий доступ сервисов к таблицам приложения не нужен: выдаём версионированный каталог
для построения индекса, а в ответ получаем его точные идентификаторы.

## Входы и результаты

| Операция | Вход | Результат |
|---|---|---|
| POST /v1/search/text | JSON: query, catalogVersion, limit | Ранжированные кандидаты; необязательный selectedId |
| POST /v1/search/image | multipart: image, catalogVersion, limit | То же; фото передаётся байтами, не путём или URL |
| POST /v1/recommendations | JSON: wineId, catalogVersion, limit | Альтернативы, без исходного вина и selectedId |

limit: целое 1–10, по умолчанию5. query: непустой текст до256Unicode-символов,
без управляющих символов. Фото: не более10MiB; валидное декодируемое JPEG/PNG/GIF,
не доверять расширению и MIME. Не более12000пикселей по стороне и25000000пикселей всего.
Ни один сервис не должен скачивать пользовательский URL, исполнять OCR-текст
или раскрывать приватные пути хранения. Фото и тело запроса не пишутся в общие логи.

Ответ: catalogVersion, modelVersion, demo и candidates: [{id, score}].
Сейчас catalogVersion=demo-v1, восемь синтетических ID из apps/api/catalog.json.
Реальный импорт потребует нового идентификатора версии и явного сопоставления
с точными slug организаторов. Нельзя выдавать synthetic ID за конкурсный slug.

- id — точное значение из согласованной версии каталога, не название вина.
- score — конечное число0…1, сигнал ранжирования, **не вероятность правильного ответа**.
- Кандидаты без повторов, по невозрастанию score; равные оценки допустимы.
- selectedId, если есть, входит в candidates и отражает решение поискового сервиса.
  Это не команда навигации UI: при нескольких результатах фото приложение всегда
  показывает список для явного выбора (FE-035, SR-001), сохраняя порядок сервиса.
- modelVersion — непустая версия реализации/модели; demo=true у заглушки.
- Эталонная заглушка проверяет формат фото, но не использует его содержимое для
  распознавания: её стабильные кандидаты — только синтетическая выдача для
  интеграции. Текстовый поиск сопоставляет название с synthetic-каталогом,
  рекомендации — фиксированные альтернативные ID. Это не измерение качества.
- Пустой candidates — успешное отсутствие результата, не ошибка зависимости.
- Чужая версия каталога/неизвестный ID — ошибка совместимости, не молчаливый пропуск.

Наш API сохраняет порядок кандидатов и берёт поля карточек из каталога.
Пока каталог синтетический, публичный ответ приложения остаётся demo=true даже
при upstream demo=false; modelVersion отражает вызванную модель. Для реального каталога
маркировка меняется отдельной согласованной миграцией.
Публичный POST /v1/search принимает прежние query/photoId; photoId разрешается
в приватное фото только в API. При query+photoId поиск идёт по query.
В настроенном режиме запрос без query и photoId даёт400 до вызова сервиса.
При настроенном сервисе параметр scenario не переключает настоящую работу на симулятор.
POST /v1/recommendations приложения принимает wineId и limit, возвращает полные карточки.

## Быстродействие и отказ

Бюджет вызова поиска по тексту/рекомендаций:1с, по фото:8с.
Общий бюджет обработки с обогащением карточек:9с. Это предельные сроки,
а не измеренный SLO модели. Для оценки p95 нужны оборудование, размер фото,
версия модели, прогретость и параллелизм; пустая заглушка скорость модели не доказывает.
Конкурсный внешний лимит10с не превращается в дополнительные10с на каждый этап.

Контекст отмены передаётся дальше. Не делать автоматических повторов тяжёлого
распознавания. Ответ ограничен по размеру. Редиректы к другим адресам запрещены.
X-Request-ID (до64символов A–Z/a–z/0–9/дефис, генерируется при отсутствии) позволяет связать вызовы без логирования фото, текста или credentials.

На публичном API: недоступность зависимости (включая её429/503) →503, таймаут →504,
отмена запроса →408, нарушенный ответ зависимости →502.
Ошибки возвращаются JSON, без stacktrace/секретов. Вход пользователя проверяется в API
до делегирования. Неожиданный400/409 внутреннего сервиса означает несовместимость
адаптера/контракта и даёт502 публичного API; это не пустой успешный результат.
Внутренний OpenAPI описывает ответы сервиса Романа; публичный — ответы нашего адаптера.
Отказ рекомендаций не ломает карточку: отдельное сообщение и повтор по действию человека.
Ненастроенный recommendation service даёт503. Настроенный, но неисправный сервис
не включает тихий fallback. Без SEARCH_SERVICE_URL сохраняется явно синтетический режим демо.

## Поведенческие сценарии

| Область | Дано / Когда | Тогда |
|---|---|---|
| Поиск текстом | Каталог известен; введено название | Идентификаторы превращаются в карточки в порядке сервиса |
| Поиск фото | Фото принято приложением; начат поиск | Передаются проверенные байты, не локальный путь; результат соответствует контракту |
| Несколько результатов фото | Несколько кандидатов с selectedId или без него | Пользователь выбирает; первый выделен, автоматического перехода нет |
| Нет совпадений | Сервис вернул пустой список | Видно состояние отсутствия результата с дальнейшими действиями |
| Альтернативы | Открыта карточка вина | Показаны другие вина; исходное вино не повторяется |
| Нет альтернатив | Рекомендаций нет | Карточка остаётся доступной, показано спокойное пустое состояние |
| Отказ | Рекомендации недоступны/медленны | Карточка и поиск работают, доступен явный повтор |
| Плохой контракт | Неизвестный ID, повторы, чужая версия, некорректный JSON |502; не выдаётся выдуманная или частичная карточка |
| Отмена | Пользователь сменил экран/вино | Запрос отменён; поздний результат не попадает на другой экран |
| Изоляция | Поиск и рекомендации на разных адресах | Каждый вызов приходит своему сервису |

Исполняемые IDs и конкретные тесты регистрируются в cases/cases.json и отчёте.
Тесты проверяют реальную HTTP-границу с локальным сервером/подменным транспортом,
без моделей, больших датасетов и ожидания реальных секунд таймаутов.
Они доказывают поведение адаптера и совместимость, но не качество рекомендаций/OCR.

## Версии и конкурс

Неизвестные дополнительные поля успешного ответа не ломают клиента; обязательные поля и типы проверяются строго.
HTTP major — /v1; совместимые дополнения повышают minor OpenAPI; несовместимые — новый major
и согласованный переход клиентов. modelVersion и catalogVersion независимы от HTTP-версии.
POST /v1/eval/predict остаётся отдельным контрактом организаторов. Эта задача не подключает
к нему заглушку, не заявляет конкурсную готовность и не меняет формат {slug}.
