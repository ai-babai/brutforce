# Поведение первого runnable demo

## Граница

Вход: выбранное пользователем изображение этикетки, ручной запрос или явное
состояние ошибки. Выход: карточка записи каталога, список кандидатов либо
понятный путь восстановления. Пользовательский путь не показывает demo-панели,
banner или технические сценарии; они существуют только на границе test/dev.

Принятый файл показывается как локальный preview и загружается в приватное
хранилище через `POST /v1/photos`. Поиск по фото получает `photoId` выданного
receipt через `POST /v1/search`; исходные байты не передаются повторно и не
попадают в публичный каталог или отчёт. Ручной поиск с любого входа использует
`GET /v2/catalog?q=…` по всему каталогу и серверную пагинацию. Номер дизайна
2.0 не задаёт версию API: major каталога появился из-за изменения его контракта
в BE-045; фото, рекомендации и конкурсный API сохраняют свои `/v1` пути.
Быстрые проверки вызывают TypeScript-компоненты React в jsdom и Go HTTP/API
напрямую; браузерная проверка записывается отдельным свидетельством.
FE-052 добавляет ручной поиск по мере ввода: от одного непустого символа,
через 250 мс после последнего изменения. Поле, загрузка и выдача остаются
на одной странице. Точные сценарии — [CAT-015…020](catalog-display-spec.md#динамический-поиск-по-мере-ввода--fe-052).

Дополнительно фиксируются camera capture JPEG → upload → receipt → search,
остановка потока камеры, восстановление после отказа разрешения и девять
правил визуального контракта Atlas. Это тесты реализации интерфейса, не
визуальная оценка в браузере и не пользовательское исследование.

## Граница заглушки

Reference-распознавание маркируется как заглушка независимо от происхождения
карточек. Настоящая карточка показывает свой URL/дату источника; её нельзя
назвать синтетической из-за reference-модели. Несовместимые версии каталога
и модели дают явную ошибку, а не подставной результат. Vitest подтверждает обработку
формы mocked API в React, а Go-тесты — HTTP-контракт в изоляции; это не
сквозная browser+Go интеграция. Они не измеряют OCR, визуальный поиск или
качество на конкурсных фотографиях. Настоящий каталог описан в
[BE-045](catalog-display-spec.md); постоянные быстрые fixtures синтетические.

## Обычная вкладка и PWA · 19.09.2026

- UI-012: Дано обычный браузер без возможности установки. Когда открыта ссылка, доступны сканирование, галерея и ручной поиск без требования установить приложение.
- UI-013: Дано браузер предложил установку. Когда человек нажал «Установить приложение», открывается системный запрос. Отмена/отказ не ломают сайт; автоматически запрос не открывается.
- UI-014: Дано запуск с домашнего экрана в standalone. Когда открывается приложение, используется тот же корневой маршрут, API и пользовательские пути; предложение установки скрыто.
- UI-015: Установочный manifest ссылается на реальные иконки192/512 и запускает / в standalone; полноэкранный режим не обязателен.
- DESIGN-010/011: При изменении доступной высоты из-за панелей браузера, safe-area или поворота превью сжимается, затвор остаётся в панели действий внутри viewport; подпись не выходит за превью.

Быстрые тесты подменяют только события установки/режим отображения и камеру. Проверки CSS фиксируют ограничения, но геометрия и установка на конкретном телефоне требуют отдельной проверки. PWA требует сети для поиска; offline и service-worker кеширование не вводятся. Обычная вкладка остаётся полноценным способом запуска.

## Нижняя навигация и каталог

- Дано старт приложения. Когда видна основная навигация, доступны Главная / Поиск / Сохранённое, текущий раздел выделен; «Главная» возвращает стартовый экран и не открывает камеру.
- Дано раздел Поиск. Когда пользователь открывает каталог, загружается первая страница до 24 вин; «Показать ещё» продолжает серверную выборку. Непустой ввод через 250 мс запускает поиск по всему каталогу; поле остаётся доступным, пустая выдача и ошибка с повтором появляются под ним. Очистка возвращает первую страницу без фильтра. Тот же путь используется при вводе по названию до открытия каталога.
- Дано открыта карточка. Когда нажато сохранение, в Сохранённом появляется ровно одна запись с тем же ID, названием, годом и изображением. Повторное открытие/перезагрузка сохраняют этот список.
- Дано сохранённая карточка. Когда удалена из списка, она исчезает; удаление последней показывает полезное пустое состояние. Ничьи загруженные фото не удаляются.
- Дано повреждённое или недоступное browser storage. Запуск не падает, ошибка постоянного сохранения не выдаётся за успех.
- Нижняя навигация не перекрывает содержимое, находится внутри настольной рамки; во время съёмки приоритет затвору. На подходящих информационных экранах подпись «Информация о российских винах».

Каталог — PostgreSQL при настроенной БД; встроенный JSON остаётся синтетическим
режимом без БД. Контракт списка и ручного поиска: [catalog-display](../../contracts/catalog-display.md).
Сохранённое — локальные снимки карточек этого браузера, без аккаунта/синхронизации.
Происхождение относится к конкретной карточке; настоящие данные не измеряют
качество распознавания. Загрузка каталога в браузер целиком не используется.

## UI-023 · Закладка карточки
Дано: открыта карточка. Когда: нажимаем Сохранить в шапке. Тогда: запись сохраняется в этом браузере, закладка заполняется, подпись становится Сохранено. Повторное нажатие удаляет только запись из сохранённого и возвращает исходное состояние, не закрывает карточку и не удаляет фото. Позиция кнопки стабильна. Ошибка записи не показывает ложный успех (UI-021); восстановление после перезагрузки проверяет UI-017. DESIGN-019 проверяет структуру и правила оформления; размеры и реальные пересечения на 320/360/390/430px и при 200% тексте — [FE-057](card-polish-spec.md).

## UI-024 / DESIGN-020 · Цельное поле поиска
Дано: открыт поиск. Когда: пользователь вводит непустой текст, результат
запрашивается автоматически через 250 мс. Лупа и Enter остаются равнозначными
способами отправить его сразу, отменяя отложенный дубль. Видимый текст IME-композиции
ищется после 250 мс даже без `compositionend`; Enter и submit во время композиции
не ускоряют поиск, завершение с тем же текстом не создаёт дубль. Пустой submit не повторяет загрузку каталога, вызванную
очисткой поля. Изменение текста сразу сбрасывает cursor и делает предыдущий
ответ неактуальным, до истечения задержки (CAT-016/018/019).
Поле и кнопка внутри общей рамки с одинаковыми скруглениями; фокус обводит всю
группу, клавиатурный фокус кнопки различим. До списка результатов минимум16px.
Поле не вылезает по горизонтали на320px. Быстрые проверки подтверждают события
и структуру; геометрия и мобильный фокус проверяются отдельно в браузере.

## Переходы v2 с уточнениями Air 3.4 · 25.09.2026

- **UI-004/UI-005.** Дано поиск по фото ещё выполняется. Когда человек отменяет его, запрос и таймер прекращаются, а главная показывает только входы камеры, галереи и поиска по названию. Снимок и receipt не предлагаются для продолжения. Поздний успех или ошибка отменённых upload/search не меняют экран. Уже загруженный приватный файл не удаляется с сервера действием Home.
- **UI-026.** Дано открыт preview исходного фото из одного из экранов пути. Когда асинхронный поиск завершился во время просмотра, закрытие preview возвращает на актуальный завершившийся экран, а не на устаревшее loading-состояние. Место входа сохраняется для главной, кандидатов, карточки и ошибки.
- **UI-027.** Дано ручной поиск уже содержит запрос и кандидатов. Когда человек открывает карточку, выбирает «Не это вино?» и возвращается назад, восстанавливаются исходная карточка, год, кандидаты и запрос; возврат не уводит самопроизвольно на главную. Для текстового пути исходного фото нет и не создаётся.
- **UI-028.** Дано фото уже принято и есть receipt. Когда поиск завершается сетевой ошибкой или ответом сервера, сообщения различимы. Повтор использует тот же receipt и не делает второй upload; успешный ответ открывает результат. Новый снимок или новый файл начинают новый путь.

Эти проверки фиксируют переходы React и границу mock API. Они не доказывают
реальную сеть, камеру, OCR или геометрию интерфейса в браузере.
BE-045 меняет транспорт ручного поиска, сохраняя возврат и контекст UI-027.
Фото-путь UI-028 продолжает различать ошибки и повторять запрос с тем же receipt.
FE-052 сохраняет UI-027, но ручная выдача, её загрузка, пустой результат и ошибка
теперь встроены в страницу поля. Они не обязаны проходить через отдельные
экраны `loading/candidates/missing/error`. Возврат из выбранной карточки
восстанавливает query, страницы, cursor и прокрутку без HTTP и без принудительного
открытия клавиатуры (CAT-020); фото-переходы UI-004/005/026/028 не меняются.

## Air 3.4 · активный фото-путь и восстановление

Согласованные продуктовые сценарии [AIR-001…024](../../design/wine-ux-v3/air/behavior-v3.feature)
уточняют переходы выше. Home или отмена завершают фото-путь и очищают клиентский
снимок/receipt; поздние ответы upload и поиска игнорируются. Открытие системной
галереи и её отмена из результатов, пустого ответа либо ошибки сохраняют исходный
экран, фото, список и прокрутку без нового HTTP. Камера и галерея остаются
отдельными действиями; прежний контекст сохраняется до принятия нового снимка.
Новый снимок создаёт новую попытку, а ответ прежней не может её подменить.

Успешный пустой фотоответ показывает «Ничего не найдено»; отказ человека от
кандидатов показывает отдельное восстановление. Сбой доставки и ошибка сервиса
показывают разные сообщения и допускают повтор поиска по тому же receipt.
Без receipt поиск не отправляется: сохранённый локальный файл может быть загружен
повторно, без гарантии единственной серверной копии. Краткая строка выдачи
показывает только известные структурированные поля, без цены, рейтинга и
процента совпадения; полная карточка сохраняет описание, источник, вкладки,
коррекцию, сохранение и рекомендации. Просмотр исходного фото и возврат из
карточки сохраняют экран входа и прокрутку без нового поиска.

Заметки в ожидании не управляют запросом; сокращение движения останавливает
автоматическое движение заметок и линии в миниатюре, оставляя читаемый статус.
Ручной поиск сохраняет CAT-015…021, в том числе IME, серверные страницы и
возврат в запрос. Оформление Air описано в [web design specs](../../apps/web/design-specs.md).
DOM/mock проверяет только поведение компонента; нативный picker, камера,
History Back, геометрия и reduced motion требуют отдельного browser review.
AIR-024 отдельно проверяет реальную геометрию камеры на 320×640 и 430×932 CSS px:
заголовок, высоту живого видоискателя, доступность съёмки и галереи над нижней
навигацией без перекрытия. CSS/DOM-проверка не закрывает этот сценарий без
браузерного измерения с действующим каскадом `v2.css` и `air.css`.


### Уточнение Макса · 21.09.2026
Выделение лидера распространяется на результаты поиска по фото, текстовый поиск
и похожие вина/рекомендации. Это заменяет прежнее ограничение SR-008 и пункт 6
handoff PR34. Первый показанный результат выделяется без процентов уверенности,
не переупорядочивая ответ. Сохранённые вина и первоначальный каталог без запроса
не являются ранжированной выдачей и не получают ложного лидера.
