## Визуальный контракт

Порядок полей у всех: полное название и линейка → производитель → год и «цвет · сахар». Название не обрезать многоточием/line-clamp, в особенности год и «Резерв». Поля брать из каталога, неизвестное не выдумывать: неизвестный год явно «Год не указан», отсутствующий производитель/тип без пустых разделителей. Фото contain; при отсутствии честная заглушка. Вся карточка — одна зона перехода, без вложенных кнопок. Лидер немного крупнее (фото 76×132, заголовок 18), остальные фото 56×98 и заголовок 14; высота строк по содержимому. Бордовый акцент, кремовая поверхность. Никаких рейтингов, цен, наград, процентов уверенности, маскота или гастросочетаний в этой выдаче. В продукт переносить существующие бренд/навигацию, не оболочку исследовательского стенда.

Одна повторная demo-фотография и вымышленные записи в эскизе нужны только для вёрстки; НЕ переносить их как реальные кандидаты, fixture должен явно оставаться синтетическим.

## Наблюдаемое поведение для BDD

1. Поиск фото вернул несколько кандидатов: показать выдачу в порядке backend; пользователь сам открывает карточку. Не перенаправлять автоматически к первому. Визуально выделить первого и нейтрально подписать «Наиболее похожее», без обещания точного совпадения и без выдуманного порога.
2. Любой кандидат (включая второй/пятый) открывает именно свою запись каталога, включая конкретный год. Не подменять идентификатор первым.
3. Возврат из карточки сохраняет порядок кандидатов, исходное фото/запрос и позицию списка. Не запускать распознавание повторно при возврате. Системная кнопка назад работает так же, как экранная.
4. «Ни одно не подходит» использует уже существующий сценарий отказа: ручной поиск или другое фото с сохранением исходного контекста до замены. Не добавлять лишний onboarding; промежуточный текст в исследовательском эскизе — граница демо, не обязательный новый экран продукта.
5. Ноль кандидатов → существующий no-match с доступным ручным поиском/пересъёмкой; не рисовать фиктивного лидера. Один кандидат → показать одну карточку без пустых мест и «ещё 4». Пять — пример, не ограничение API. Не менять backend ранжирование.
6. Поиск по имени не получает бейдж «Наиболее похожее» только по позиции в списке. Поручение касается результата распознавания фото; не менять другие поисковые сценарии без основания.
7. Длинные названия, одинаковая линейка с разными годами, неизвестные поля, отсутствующее/сломанное фото: без наложений, обрезания различающих слов и горизонтального скролла на 320/390/430 px. Проверить текст 200% и клавиатуру; focus виден, название кнопки содержит имя и год.

## Реализация и проверки

Sigma BDD: сначала сопоставить с текущими контрактами и живыми сценариями приложения в своей рабочей ветке. Добавить поведенческие спеки и meaningful tests на несколько результатов, выбор не первого, возврат без нового запроса, ноль/один результат, no-match fallback. Затем реализовать экран и синхронизировать канонический v2-макет/дизайн-систему, если они поддерживаются отдельно. Визуально проверить реальные экраны на мобильных ширинах; существующие ошибки сети/камеры и сохранение фото не регрессировать. Пользователь разрешил начать реализацию; отдельного запроса на новый production deployment в этом поручении нет. Отчитаться ссылкой на задачу/PR, проверками и статусом запуска. Не объявлять качество распознавания улучшенным по UI-тестам.
