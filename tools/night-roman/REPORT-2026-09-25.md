# N4 Roman judge over B: result and scope

The same Roman `fullframe-qlora-lr1e-4-v1` adapter was evaluated two ways
against the fixed B candidate pool: a five-card judge and a twenty-card
four-group tournament. Both use the pinned Qwen3.5-4B base and the recorded
runtime-linear vision patch implementation. No training was performed.

| Profile | Frozen service (141 graded, 151 submitted) | Frozen retrieval Top1 / Top5 / Top20 (62 graded) | Organizer exact Top1 / Top5 / Top20 (54 unique exact) |
|---|---:|---:|---:|
| B, no judge | 114 | 57 / 59 / 62 | 44 / 51 / 53 |
| Pinned base without LoRA, five cards | 114 | 57 / 59 / 62 | 44 / 51 / 53 |
| Roman adapter, five cards | 116 | 58 / 59 / 62 | 46 / 51 / 53 |
| Roman adapter, twenty-card tournament | **120** | **61 / 62 / 62** | **50 / 52 / 53** |

All rows are included: 213 frozen v2 requests and 103 organizer requests.
Organizer scoring uses the corrected local diagnostic labels; 54 of 100
unique images have exact targets. The Roman-20 profile had six graded frozen
service fixes and four retrieval fixes relative to B, with no graded
regressions in these snapshots. Twenty-card judging falls back to B when a
required exact reference is excluded; five-card judging falls back when its
first five include an excluded reference. No excluded reference was replaced.

Roman's native 590-candidate cascade cannot be reconstructed because the
immutable handoff lacks two ancestor arrays. This experiment measures Roman
judging on B's candidate pool; it does not reproduce Roman's 715/2033
development result. The runtime-linear vision patch is mathematically
equivalent but BF16 differences can affect close digit logits. Seven Roman-5
Top1 changes were checked against the original Conv3d operator and kept the
same selected candidate; this does not make every Roman-20 output bitwise
equivalent. Exact SHA overlap with Roman's listed training and validation
query bytes was zero for 212 unique frozen and 100 unique organizer images,
which does not rule out recodes, crops, related scenes, or shared labels.
These are development results, not an independent untouched test.

The cached-pool submissions report Qwen processor-and-model time after image
decode and card assembly. Fresh B→Roman HTTP timing is a separate run and
includes both stages, transport, and a strict 10-second client deadline. Its
results were exported separately after all 316 requests finished. Gold stays in
the trusted local scorer; the GPU pod receives only public fields and images.

Artifacts: `/Users/skif/ml-data/brutforce/night-20260925/roman/final/` has
full submissions and paired predictions;
`/Users/skif/ml-data/brutforce/night-20260925/roman/scores/final/` has local
scores; `overlap-audit.json`, `conv3d-decision-check.jsonl`, and
`run-config.json` record safeguards and provenance. `final/export-validation.json`

## First fresh HTTP run: full pipeline and deadline

The pinned B service and Roman20 server ran on one RTX 4090. The client sent
all 316 original images over local HTTP, with a 10-second timeout per request.
The cascade obtained every B Top20 through a fresh B call, rather than reading
saved predictions. It returned Roman-5 group-zero and Roman-20 ranks together.

| Profile | Frozen service (141 graded) | Frozen retrieval Top1 / Top5 (62 graded) | Organizer exact Top1 / Top5 / Top20 (54 unique exact) |
|---|---:|---:|---:|
| Roman-5 output of full Roman-20 endpoint | 101 | 58 / 59 | 42 / 46 / 48 |
| Roman-20 full endpoint | **104** | **61 / 62** | **45 / 47 / 48** |

There were 291 timely HTTP responses and 25 timeouts: 16 in frozen service,
none in frozen retrieval, and 9 in the organizer basket. Median local client
latency was 6.45 seconds. Every timeout remains a failed request in the scores.
All 316 server-complete fresh B, Roman-5, and Roman-20 ranks exactly match the
cached-pool run, including the late 25. Thus the cached 120/141 service and
50/54 organizer exact Top1 for Roman-20 are a directly checked no-deadline
quality upper bound, while 104/141 and 45/54 are observed deadline scores.
The source-bound export is in `live-http-v1-final/`; source hashes, B catalog
and index hashes, and the 10-second timeout are in
`live-http-v1-provenance/runtime-config.json` under the data artifact root.

The unmodified organizer `participant_test.sh` accepted the ephemeral
multipart adapter: it parsed four slugs from six fixed public images, and
returned null on two 10-second curl timeouts. The adapter completed all six
on the server. A separate raw curl recorded HTTP 200, a one-slug JSON body,
95,742 bytes uploaded, and 3.291 seconds through the SSH tunnel for one case.
These external tunnel/upload times are separate from the local 316-request
client measurement. See `competition-smoke/report.json` under the data root.

The output-preserving `--ocr-threads 6` check had exact B rank/action parity
on five slow cases but no consistent speed gain; median B time worsened from
5.09 to 5.53 seconds. Paddle MKLDNN was rejected: it made OCR raise an
`NotImplementedError` containing `ConvertPirAttribute2RuntimeAttribute not
support [pir::ArrayAttribute<pir::DoubleAttribute>]`. B caught that error,
returned `ocr_error` with empty OCR text, and changed all five tested ranks;
the apparent subsecond OCR timings are failed calls, not an acceleration.
A follow-up should make this deliberate degraded no-OCR fallback visible in monitoring
instead of allowing it to masquerade as a fast successful request. The pinned
models all reside on CUDA; measured Base224 GPU forward
took roughly 0.01–0.02 seconds while its image processor took 0.20–0.47
seconds on those cases. OCR was the dominant variable stage at 2.81–7.58
seconds. These are diagnostic measurements, not independent latency proof.

## OCR input resize as a separate quality variant

A second full HTTP profile bounded Paddle's BGR OCR input to 1280 pixels on
the longest side before calling the unchanged OCR model. It kept the original
B detector, index, catalog, OCR thread count, Roman adapter, and Roman20
tournament. It is a separate quality configuration because resampling changed
recognition results.

The full 316-request run had 281 timely responses and 35 timeouts. Roman20
scored 100/141 frozen service, 61/62 retrieval Top1 (one timeout), and 39/54
unique organizer exact Top1, below the unchanged B→Roman20 run at 104/141,
61/62, and 45/54. Across paired requests, the selected bottle and label
boxes did not change; OCR text changed in 184 requests, B Top20 in 134,
B Top1 in 15, and Roman20 Top1 in 10. B p50/p95 rose from 3.90/7.62 seconds
to 4.03/7.93 seconds. Four old timeouts became timely, but 14 old timely
requests timed out. The measured regression rules out promoting this resize.
The full evidence is under `live-ocr1280-final/` and
`live-ocr1280-provenance/` in the data artifact root.

## Original-B deadline policy, full 316 requests

The next profile restored the unchanged B OCR input and original two OCR
threads. A fixed timing-derived policy returned fresh B rankings when B had
already taken at least 6 seconds, skipping Roman; otherwise it ran the same
Roman-20 tournament. The threshold came from latency in the earlier
development HTTP run, without inspecting gold for threshold selection. It is
not an independently validated service-level guarantee. The server handles
one request at a time and launches no background judge after a fallback.

The strict 10-second client completed 315/316 requests: 212/213 frozen and
103/103 organizer. The only timeout was frozen `case-000106`, where B alone
took 13.03 seconds. Twenty-seven timely requests used the B fallback (13
frozen, 14 organizer). Client median was 5.94 seconds and p95 was 8.46
seconds. One more B≥6-second request is the timeout. All responses retain
the full Top20 basket and the original image hashes.

| Profile | Frozen service (141 graded) | Frozen retrieval Top1 / Top5 (62 graded) | Organizer exact Top1 / Top5 / Top20 (54 unique exact) |
|---|---:|---:|---:|
| Roman-5 output of full Roman-20 endpoint with B fallback | 116 | 58 / 59 | 46 / 51 / 53 |
| Roman-20 endpoint with B fallback | **119** | **61 / 62** | **48 / 51 / 53** |

This improves the observed deadline result over the first full Roman-20 HTTP
profile (104 service, 45 organizer exact Top1), while retaining one B-only
timeout. Because 27 requests deliberately skip Roman, these numbers measure
the **B→Roman-20-or-B policy**, not Roman judging on every request. Roman-5
in this table still pays for the full Roman-20 endpoint. The independent
Roman-5-only timing control is reported separately when its full run ends.
Raw client and server records, logs, source and config hashes are under
`live-deadline6-provenance/`; complete predictions, six local scores, and
coverage are under `live-deadline6-final/` in the data artifact root.

## Standalone Roman-5 full HTTP control

The final full 316-request profile restored original B, removed the deadline
fallback, and called only the first-five Roman adapter judge. No Roman-20
group or final judging ran. This measures Roman-5's own end-to-end latency,
which the earlier shared-endpoint Roman-5 outputs could not do.

The strict client had 314/316 timely responses: 211/213 frozen and 103/103
organizer. Frozen `case-000106` and `case-000122` timed out. Client median was
3.93 seconds, p95 7.04 seconds. Service scored **115/141**, retrieval
**58/62 Top1** and 59/62 Top5, and organizer **46/54** unique exact Top1,
51/54 Top5, 53/54 Top20. All 314 timely fresh B and Roman-5 ranks matched
the cached-pool run; the two timeouts remain failed. The offline Roman-5
116/141 and 46/54 is a checked no-deadline upper bound for this input set.

Compared with the original unchanged-B Roman-20 full endpoint, standalone
Roman-5 saved client time and substantially reduced timeouts, while Roman-20
ranked more frozen service and retrieval examples correctly without a
deadline. The timing-derived B fallback profile reached higher observed
quality than either constant-judge endpoint under these specific 10-second
development requests, but it leaves hard B-only tails such as `case-000106`.
None of these figures validates a future organizer SLA independently.

Raw client/server logs, the 316-row standalone server slice, exact source and
config hashes are under `live-roman5-provenance/`; full predictions, three
trusted local scores, and coverage are under `live-roman5-final/`. The replay
asset archive and hashes are under `replay-assets/`, and exact Python/GPU/CPU
environment snapshots are under `environment/`. The dedicated B and Roman
HTTP processes were stopped after artifacts were copied and scored. No
production or test service was modified; no Sigma authorized key or system
configuration was changed.
