# Архитектура BrutForce

[Начало](README.md) · [Запуск на своей машине](docs/SELF-HOST.ru.md) · [Контракты API](contracts/README.md)

Система решает две связанные задачи: конкурсный клиент запрашивает **один slug** по фотографии, а мобильное приложение показывает **существующую карточку**. Эти результаты не тождественны: каталог организаторов и импортированный каталог витрины имеют разное покрытие.

## Сервисы и границы

```text
браузер --> apps/web (React) --> apps/api (Go HTTP API)
                                   |-- /v2/catalog, поиск по названию --> PostgreSQL
                                   |-- /v1/photos --> приватный volume uploads
                                   |-- /v1/recommendations --> JSON похожих карточек
                                   `-- /v1/search (photoId) --> vision (Python CPU)
                                                                 |-- веса + OCR
                                                                 `-- визуальный индекс
                                                       --> slug --> карточка в PostgreSQL

организатор -- POST /v1/eval/predict (image) --> Go API --> тот же vision
                                                    `--> один проверенный slug
```

Изображения карточек `catalog-media/` отдаются браузеру файловым web-proxy;
они не являются эталонными фото, из которых построен визуальный индекс.

В [минимальном режиме](docs/SELF-HOST.ru.md#минимальный-режим-без-docker) один Go-процесс обслуживает собранный UI и встроенный синтетический каталог из восьми записей. PostgreSQL и сервис распознавания не запускаются; `/v1/eval/predict` отвечает 503. [Минимальный Compose](deploy/compose.demo.yaml) упаковывает тот же путь в один контейнер.

В [полном Compose](deploy/compose.yaml) используются PostgreSQL 18, одноразовый импорт каталога, Go API с веб-сборкой, read-only CPU-сервис распознавания и файловое хранилище фото. Веб-контейнер публикуется на `127.0.0.1:8097`, внутренний ML-сервис доступен Go API на `vision:8127`, база извне не публикуется. Файлы модели монтируются read-only, а база, загрузки, feedback и снимки каталога хранятся в отдельных Docker volumes. Это профиль для **точного** внешнего комплекта данных, а не способ скачать его из Git.

[Главная страница](README.md#краткая-архитектура) показывает короткую схему; [инструкция по запуску](docs/SELF-HOST.ru.md#данные-для-полного-режима) описывает внешний комплект. В полном Compose его пути соответствуют следующим подключениям:

```text
ХОСТ: ~/brutforce-local/            КОНТЕЙНЕР / НАЗНАЧЕНИЕ
|-- f8-bundle/                       /assets:ro (vision + web)
|   |-- onnx/vision.onnx             Визуальный энкодер SO400M
|   |-- models/hub/                  HF-модели детектора и вспомогательного энкодера
|   |-- ocr/{rus,eng}.traineddata    Языки Tesseract
|   |-- index/{index.npz,index-info.json} Векторы и их provenance, 2 103 slug
|   |-- catalog/catalog-bundle.json  Эталоны организаторов (не каталог витрины)
|   `-- overlay/organizer-slugs.json Допустимые slug для Go API
|-- catalog-package/                /catalog-package:ro (migrate: JSONL/manifest)
|-- catalog-media/                  /catalog-media:ro (migrate + web: WebP карточек)
|-- recommendations/index.json      /recommendations/index.json:ro (web: 2 038 ID)
`-- secrets/{db_password,app_password} Docker secrets (создать на месте)

GIT: apps/vision/                     КОД (собирается в образ, не в архив)
|-- overlay/night_server.py           CPU-сервис и OCR rescue
|-- overlay/spec/lexicon.json         Фиксированная политика OCR
`-- parent/*.py                       Детектор, эмбеддинг, поиск и HTTP-обработчик

Docker volumes, а не папки из архива:
|-- db-data      PostgreSQL: импортированные карточки, алиасы, версия
|-- uploads      Приватные оригиналы и receipt загруженных фото
|-- feedback     Локальные ответы/разметка, отдельно от модели
`-- catalog-snapshots Снимки импорта каталога для восстановления
```

Состав внешних данных закреплён [SHA-манифестом](deploy/assets/f8-cpu.sha256); [перенос и пересборка индексов](docs/ASSET-TRANSFER.ru.md) объясняют, что готовый индекс работает без исходных эталонных WebP, но для его пересборки эти фотографии нужны. Пять абсолютных путей задаются через [пример env](deploy/docker.env.example), а не записаны в образ. [Исходный Python-код](apps/vision/README.md), [bridge](scripts/docker-vision-bridge.py), [Dockerfile vision](deploy/Dockerfile.vision), миграции/импортёр `apps/api/` и контракты находятся в Git; веса и каталожные данные — вне Git.

## Путь фотографии в приложении

1. Браузер отправляет `POST /v1/photos` с multipart-полем `photo`. API проверяет тип по байтам и лимиты, сохраняет оригинал **приватно** вне web root и возвращает случайный `photoId`. Фото не выдаётся по публичному URL.
2. Браузер отправляет `POST /v1/search` с JSON `{"photoId":"..."}`. API читает проверенные байты по receipt и направляет их в CPU-сервис; для ручного поиска по названию он читает каталог без модели.
3. CPU-сервис учитывает поворот из EXIF, приводит фото к RGB, выбирает область бутылки или этикетки и строит признаки для поиска по эталонам. Он возвращает ранжированные идентификаторы `slug` из зафиксированного списка организаторов. Go проверяет версии индекса/каталога и допустимость slug, а затем разрешает их в **существующие** ID карточек PostgreSQL. Неизвестный результат, ошибка сервиса и отсутствие карточки — разные исходы.
4. UI показывает найденные карточки, если они есть. Когда лучший slug организаторов существует, но соответствующей карточки витрины нет, `/v1/search` возвращает `outside_display_catalog`; чужая карточка не подменяет точную. Дополнительные предложения из `POST /v1/recommendations` берутся из отдельного каталожного индекса и не считаются доказательством распознавания.

Схемы и ошибки: [загрузка](contracts/photo-upload.md), [распознавание/сопоставление](contracts/vision-serving.md), [карточки](contracts/catalog-display.md).

## Путь запроса организатора

```sh
curl --fail-with-body --max-time 10 -F 'image=@/path/to/approved-photo.jpg' \
  http://127.0.0.1:8097/v1/eval/predict
```

`POST /v1/eval/predict` принимает **одно** multipart-поле `image`, не `photoId`. Оригинальное фото по этому пути не записывается в uploads. Go проверяет размер и геометрию: кадры свыше 25 млн пикселей (до 50 млн) уменьшает до длинной стороны не более 4 000 пикселей. Проверенные байты отправляются в тот же CPU-сервис. Для [загрузки в приложении](contracts/photo-upload.md) действуют свои лимиты. Go проверяет slug по закреплённому списку организаторов и отвечает плоским JSON `{"slug":"wine-slug"}` без требования карточки витрины.

Выданный организаторами `participant_test.sh` отправляет фото последовательно; его локальный адрес по умолчанию `127.0.0.1:8080`, для своего сервера используется `--endpoint`. Скрипт считает предсказанием только непустую строку slug из ответа HTTP 200/201 за 10 секунд; без неё пишет `null`. [Точный контракт](contracts/eval-predict.md).

## Модель и поиск

Действующая CPU-конфигурация использует детектор/выбор области этикетки (RT-DETR и OWLv2), визуальный энкодер **SigLIP2 SO400M** и закреплённый индекс признаков эталонных фото. Модель превращает область изображения в признаки, по которым индекс ищет кандидатов. Текстовое подтверждение и OCR используются при неоднозначности; выход — ранжированные slug, **не** сгенерированные описания вина. Сервер Go не обучает модель и не выводит факты карточки из текста модели. Детальный порядок ветвей определён [кодом CPU-сервиса](apps/vision/README.md).

Для воспроизведения нужны внешние веса ONNX и моделей детекции, processor/tokenizer, индекс, список допустимых slug и OCR-данные. Код и lexicon входят в `apps/vision/`. [Опись и ревизии](deploy/assets/INVENTORY.md) ссылаются на исходные модели; [32 SHA](deploy/assets/f8-cpu.sha256) закрепляют точные байты внешних данных. [Проверяющий скрипт](scripts/asset-bundle.py) принимает уже имеющиеся файлы и не загружает их. Образ [vision](deploy/Dockerfile.vision) использует Python 3.12 и CPU-зависимости из `deploy/assets/vision-requirements.txt`; `f8-bundle` монтируется read-only. Дополнительный индекс рекомендаций и пакет каталога монтируются отдельно.

Никакой токен команды для запросов к локальному API не нужен. Веса и данные **не находятся** в Git: [комплект доступен отдельно](https://disk.yandex.ru/d/dHAXDPcitS-ZJQ), но права на повторное распространение не подтверждены. Публичная ссылка сама по себе не доказывает запуск на чистой Linux-машине или OCR-паритет. [Что реально проверено](docs/SOLUTION.md#воспроизведение-и-ограничения).
