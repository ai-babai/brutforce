# Архитектура BrutForce

[Начало](README.md) · [Запуск на своей машине](docs/SELF-HOST.ru.md) · [Контракты API](contracts/README.md)

Система решает две связанные задачи: конкурсный клиент запрашивает **один slug** по фотографии, а мобильное приложение показывает **существующую карточку**. Эти результаты не тождественны: каталог организаторов и импортированный каталог витрины имеют разное покрытие.

## Сервисы и границы

```text
                   ┌───────────────────────────────────────────────┐
браузер            │ apps/web: React/TypeScript, мобильный экран   │
  │                └────────────────────────┬──────────────────────┘
  │  /v1/photos (photo), /v1/search (photoId), /v2/catalog, /v1/recommendations
  ▼                                         ▼
             apps/api: Go HTTP API ──→ PostgreSQL: карточки витрины
                    │      │           + алиасы и версия каталога
                    │      ├─────────→ приватные uploads/feedback
                    │      └─────────→ отдельный индекс рекомендаций
                    ▼
             CPU-сервис распознавания ──→ индекс эталонных изображений
             (код и веса вне Git)          + список slug организаторов

организатор ── POST /v1/eval/predict (image) ──→ Go API ──→ CPU-сервис
                                                    └──→ один проверенный slug
```

В [минимальном режиме](docs/SELF-HOST.ru.md#минимальный-режим-без-docker) один Go-процесс обслуживает собранный UI и встроенный синтетический каталог из восьми записей. PostgreSQL и сервис распознавания не запускаются; `/v1/eval/predict` отвечает 503. [Минимальный Compose](deploy/compose.demo.yaml) упаковывает тот же путь в один контейнер.

В [полном Compose](deploy/compose.yaml) используются PostgreSQL 18, одноразовый импорт каталога, Go API с веб-сборкой, read-only CPU-сервис распознавания и файловое хранилище фото. Веб-контейнер публикуется на `127.0.0.1:8097`, внутренний ML-сервис доступен Go API на `vision:8127`, база извне не публикуется. Файлы модели монтируются read-only, а база, загрузки, feedback и снимки каталога хранятся в отдельных Docker volumes. Это профиль для **точного** внешнего комплекта данных, а не способ скачать его из Git.

| Часть | В репозитории | Вне репозитория |
|---|---|---|
| UI и API | `apps/web/`, `apps/api/`, схемы в `contracts/` | приватные загруженные фотографии |
| Распознавание | [обёртка запуска](scripts/docker-vision-bridge.py), [Dockerfile](deploy/Dockerfile.vision), [SHA-манифест](deploy/assets/f8-cpu.sha256) | код модели и детектора, веса, tokenizer/processor, ONNX, индекс эталонов, OCR-данные |
| Каталог | миграции/импортёр в `apps/api/`, [формат пакета](contracts/catalog-display.md) | JSONL-пакет витрины, WebP media, список slug организаторов |
| Рекомендации | HTTP-маршрут и SHA-проверка | индекс похожих **карточек витрины**, отличный от визуального индекса модели |

## Путь фотографии в приложении

1. Браузер отправляет `POST /v1/photos` с multipart-полем `photo`. API проверяет тип по байтам и лимиты, сохраняет оригинал **приватно** вне web root и возвращает случайный `photoId`. Фото не выдаётся по публичному URL.
2. Браузер отправляет `POST /v1/search` с JSON `{"photoId":"..."}`. API читает проверенные байты по receipt и направляет их в CPU-сервис; для ручного поиска по названию он читает каталог без модели.
3. CPU-сервис возвращает ранжированные идентификаторы `slug` из зафиксированного списка организаторов. Go проверяет версии индекса/каталога и допустимость slug, а затем разрешает их в **существующие** ID карточек PostgreSQL. Неизвестный результат, ошибка сервиса и отсутствие карточки — разные исходы.
4. UI показывает найденные карточки, если они есть. Когда лучший slug организаторов существует, но соответствующей карточки витрины нет, `/v1/search` возвращает `outside_display_catalog`; чужая карточка не подменяет точную. Дополнительные предложения из `POST /v1/recommendations` берутся из отдельного каталожного индекса и не считаются доказательством распознавания.

Схемы и ошибки: [загрузка](contracts/photo-upload.md), [распознавание/сопоставление](contracts/vision-serving.md), [карточки](contracts/catalog-display.md).

## Путь запроса организатора

```sh
curl --fail-with-body --max-time 10 -F 'image=@/path/to/approved-photo.jpg' \
  http://127.0.0.1:8097/v1/eval/predict
```

`POST /v1/eval/predict` принимает **одно** multipart-поле `image`, не `photoId`. Оригинальное фото по этому пути не записывается в uploads. Go отправляет байты в тот же CPU-сервис, проверяет slug по закреплённому списку организаторов и отвечает плоским JSON `{"slug":"wine-slug"}` без требования карточки витрины. Выданный организаторами `participant_test.sh` отправляет фото последовательно; его локальный адрес по умолчанию `127.0.0.1:8080`, для своего сервера используется `--endpoint`. Скрипт считает предсказанием только непустую строку slug из ответа HTTP 200/201 за 10 секунд; без неё пишет `null`. [Точный контракт](contracts/eval-predict.md).

## Модель и поиск

Действующая CPU-конфигурация использует детектор/выбор области этикетки (RT-DETR и OWLv2 в комплекте), визуальный энкодер **SigLIP2 SO400M** и закреплённый индекс признаков эталонных фото. Модель превращает область изображения в признаки, по которым индекс ищет кандидатов. Текстовое подтверждение и OCR используются при неоднозначности; выход — ранжированные slug, **не** сгенерированные описания вина. Сервер Go не обучает модель и не выводит факты карточки из текста модели. Детальный порядок ветвей определяется внешним кодом bundle, а не этой схемой.

Для воспроизведения нужны веса ONNX и моделей детекции, processor/tokenizer, код сервиса и родительских модулей, индекс, список допустимых slug и OCR-данные. [Опись и ревизии](deploy/assets/INVENTORY.md) ссылаются на исходные модели; [50 SHA](deploy/assets/f8-cpu.sha256) закрепляют точные байты экспортируемого комплекта. [Проверяющий скрипт](scripts/asset-bundle.py) принимает уже имеющиеся файлы и не загружает их. Образ [vision](deploy/Dockerfile.vision) использует Python 3.12 и CPU-зависимости из `deploy/assets/vision-requirements.txt`; экспортированный bundle (в скриптах он называется `f8-bundle`) подключается read-only. Дополнительный индекс рекомендаций и пакет каталога монтируются отдельно.

Никакой токен команды для запросов к локальному API не нужен. Веса и данные **не находятся** в Git: права на их распространение и открытый канал передачи полного комплекта пока не подтверждены. Поэтому полный запуск на чистой машине и OCR-паритет нельзя объявить проверенными только по этому README. [Что реально проверено](docs/SOLUTION.md#воспроизведение-и-ограничения).

## Развёртывание команды

Прототип [app.dzap.pw](https://app.dzap.pw) использует ту же границу Go ↔ CPU-сервис, но запущен командой отдельно через systemd и контроллер выпуска; его каталоги и адреса не нужны для локального режима. [Порядок TEST → PROD и восстановления](deploy/PIPELINE.md) относится к внутренней эксплуатации, а не к первому запуску внешнего читателя.
