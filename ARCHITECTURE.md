# Архитектура BrutForce · 28.09.2026

В TEST и [PROD](https://app.dzap.pw) работает CPU F8 за Go API. Развёрнутый app — `d26afa3`, candidate — `b0428147…`. Полную связку с каталогом и индексами хранят в закрытой квитанции выпуска; [PIPELINE](deploy/PIPELINE.md) задаёт порядок её сверки. Документация вошла в приватный `main` на `b451ecd` и обновляется отдельно от приложения.

PROD HTTPS и HTTP-путь с реальным фото проверены 28 сентября 2026; браузер и камера на устройстве ждут отдельной проверки. Схемы API задают [контракты](contracts/README.md).

## Приложение и данные

```text
 пользователь → мобильный React/TypeScript UI → Go API ──→ PostgreSQL (карточки)
                                              ├──→ приватные фото и feedback
                                              ├──→ закреплённый индекс рекомендаций
                                              └──→ CPU F8 (фото → ранжированные slug)

 конкурсный клиент → POST /v1/eval/predict → Go API → CPU F8 → проверенный slug
```

Конкурсный запрос принимает multipart `image` и возвращает один проверенный slug; исходное фото по этому маршруту не сохраняется. Без модели API отвечает 503. [Контракт запроса](contracts/eval-predict.md).

Приложение сохраняет загруженное фото приватно: `POST /v1/photos` выдаёт `photoId`, затем `POST /v1/search` отображает до пяти существующих карточек. Если лучший slug организатора отсутствует в каталоге витрины, API [сообщает об этом](contracts/vision-serving.md), не назначая более низкий результат точным совпадением.

Ручной поиск читает каталог; выдача страниц формируется на стороне API. Дополнительная функция — рекомендации из отдельного закреплённого индекса по тексту карточек и атрибутам винодельни, без анализа предпочтений пользователя.

## Реальный CPU F8 в TEST и PROD

```text
входное фото
    → проверка формата/размеров + подготовка изображения
    → детектор этикетки / gate (кандидатные области и выбор пути)
    → SO400M визуальные признаки → поиск в версионированном индексе
    → текстовое подтверждение / OCR rescue при недостаточном визуальном сигнале
    → ранжированные slug из закреплённого списка организатора
    → Go: проверка версий и allowlist → ID карточки витрины / явная недоступность
```

Это схема функции, а не точный порядок всех внутренних ветвей. [Манифест bundle](deploy/assets/f8-cpu.sha256) закрепляет 50 файлов F8: код и parent imports, веса, препроцессинг, OCR-лексикон и индекс. `deploy/f8-runtime.json` хранит версии и SHA шести внешних файлов серверного выпуска, но не весь bundle.

Веса, оригинальные снимки и выгрузка каталога находятся вне Git. Манифесты позволяют сверить bytes после передачи; доступ эксперта к ним и воспроизведение на чистом Linux ещё не подтверждены. [Получение и проверка](docs/RUNBOOK.ru.md#полный-cpu-профиль-f8), [vision-контракт](contracts/vision-serving.md).

GPU-кандидат и переключение GPU→CPU при сбое остаются отдельной проверкой; действующий маршрут TEST/PROD — CPU F8. Локальное демо использует синтетические ответы для проверки интерфейса. Качество распознавания оценивают по фото с известными ответами, а не по health. [Результаты и ограничения](docs/SOLUTION.md).

## Выпуск и граница доступа

TEST и PROD используют раздельные приложения/API и базы PostgreSQL, а CPU F8 общий. [Контроллер выпуска](deploy/PIPELINE.md) закрепляет кандидат и процедуру отката: прежняя страница возвращается с сохранением данных; SQL schema автоматически не откатывается.

Для локального воспроизведения подготовлен Docker Compose, но передача assets, сборка и parity ещё ожидают проверки. PROD работает через systemd. Секреты и пользовательские фото остаются вне Git и release archives.
