# Архитектура BrutForce · 28.09.2026

Состояние: CPU F8 подключён в TEST к Go API; текущий исходный baseline TEST `d26afa3`, candidate `b0428147` (полную effective-связку, включая data overrides, сверять с серверным журналом). PROD на [app.dzap.pw](https://app.dzap.pw) пока заглушка. [Контракты](contracts/README.md) — источник схем API; эта страница описывает устройство, не переопределяет их.

## Приложение и данные

```text
пользователь → React/TypeScript mobile UI
                   │ photo / text / card / recommendations
                   ▼
              Go HTTP API ─────────────→ PostgreSQL display catalog (ID, slug, карточки)
                 │     │                               ↑ отдельная миграция/импорт
                 │     ├──→ приватные upload receipts и feedback (вне WEB_ROOT)
                 │     └──→ визуальные соседи (SHA-прикреплённый offline index)
                 │
                 └──→ внутренний CPU vision F8 (image → ранжированные organizer slugs)

конкурсный клиент → POST /v1/eval/predict → Go API → тот же F8 → первый проверенный slug
```

Конкурсная граница получает multipart `image`, не записывает фото и выдаёт один slug при точном распознавании; отсутствие модели означает 503. Путь приложения `POST /v1/photos` → приватный `photoId` → `POST /v1/search` сверяет исходные байты, затем отображает максимум пять существующих карточек. Если лучший organizer slug отсутствует в display-каталоге, ответ [явно сообщает об этом](contracts/vision-serving.md); более низкий кандидат не становится «точным» автоматически. Ручной текстовый поиск читает каталог, рекомендации строятся отдельно из соседей **визуальных признаков**, а не из личных предпочтений или результатов текущего фото. Каталог выдаётся страницами API, не загружается целиком в браузер.

## Реальный CPU F8 в TEST

```text
входное фото
    → проверка формата/размеров + подготовка изображения
    → детектор этикетки / gate (кандидатные области и выбор пути)
    → SO400M визуальные признаки → поиск в версионированном индексе
    → текстовое подтверждение / OCR rescue при недостаточном визуальном сигнале
    → ранжированные slug из закреплённого списка организатора
    → Go: проверка версий и allowlist → ID карточки витрины / явная недоступность
```

Это функциональная схема: набор и порядок внутренних ветвей конкретного F8-кода, веса, OCR-лексикон, индекс и правила gate должны быть закреплены в **полном** asset manifest при упаковке. `deploy/f8-runtime.json` фиксирует mode/model/catalog/index и SHA только шести внешних файлов; сам по себе не охватывает все parent imports, веса и зависимости и не даёт права обещать воспроизводимость. Внешние файлы, оригинальные снимки и каталожные выгрузки не находятся в Git. [Получение assets и проверка](docs/RUNBOOK.ru.md#полный-cpu-профиль-f8), [контракт vision](contracts/vision-serving.md).

CPU F8 — подтверждённый TEST backend; GPU-кандидат и маршрутизация GPU→CPU обсуждаются/проверяются отдельно, не являются подтверждённым текущим режимом TEST или PROD. DEMO/reference без vision остаётся только синтетическим проверочным контуром, а не ML-решением. Без полного набора и известных ответов health-сигнал сервиса не доказывает качество распознавания. [Метрики и ограничения](docs/SOLUTION.md).

## Выпуск и граница доступа

На сервере TEST приложение/API, F8 и PostgreSQL — отдельные процессы/хранилища под [контроллером выпуска](deploy/PIPELINE.md). Первый PROD планируется по проверенной CPU-связке и отдельному approval; rollback первого выпуска возвращает прежнюю страницу и сохраняет данные. Docker/Compose для локального воспроизведения готовит отдельная ветка; пока не подтверждены asset access и parity, нельзя приписывать контейнеру работающий PROD. Секреты среды и пользовательские фото хранятся вне Git и не становятся частью скриншотов или release archives.
