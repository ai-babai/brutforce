# Архитектура Vino

Статус: `proposed-baseline`. Это начальная граница компонентов для исследований,
а не принятое решение о конкретном фреймворке или модели.

## Главный инвариант

Один и тот же идентификатор позиции проходит без неоднозначного преобразования
через каталог, индекс, retrieval, reranker, confidence policy, API и карточку.
Оценочный endpoint возвращает точный каталожный `slug` или терминальный отказ.

## Логический pipeline

```text
camera/gallery image
        |
        v
validation -> normalization/crop/perspective/glare handling
        |
        v
visual feature extractor ----> closed-set Svoe index
        |                         + open-world RU variant library
        +---------- retrieval <---------------+
                       |
                       v
            near-duplicate reranker
              + optional OCR signal
                       |
                       v
       family/variant/catalog resolver
                       |
           calibrated confidence policy
              | current exact | external/uncertain
              v               v
        {"slug":"..."}   not_found
              |
              v
         catalog wine card -> post-search feature
```

## Границы компонентов

1. **Catalog ingestion** — валидирует JSON/CSV, нормализует source SKU и строит
   версионируемые снимки каждого каталога без forced crosswalk.
2. **Image intake** — проверяет MIME/signature, размер, декодирование, лимиты и
   создаёт производную копию без EXIF.
3. **Normalization** — детерминированные операции, параметры которых входят в
   конфиг эксперимента.
4. **Feature extraction** — CV-модель за стабильным интерфейсом. SigLIP 2 —
   первый кандидат, но baseline должен включать простое сравнение признаков.
5. **Retrieval** — top-K по визуальному вектору в closed-set индексе и
   open-world библиотеке вариантов. Реализация индекса меняется без изменения
   внешнего API.
6. **Reranking** — различает похожие позиции по локальным визуальным областям,
   сезону/году/категории; OCR допускается только как дополнительный измеренный
   сигнал.
7. **Family/variant resolver** — различает точный текущий SKU, тот же wine family
   другого винтажа/редизайна и внешнее российское вино без текущего `slug`.
8. **Confidence policy** — откалиброванный порог, top-1/top-2 margin и правила
   отказа. Не выдаёт низкоуверенный или только family-level кандидат как exact
   SKU.
9. **Catalog API** — по `slug` возвращает карточку; не смешивается с поисковой
   уверенностью.
10. **Web UI** — mobile-first загрузка, понятные состояния, карточка и
   восстановление после ошибки.
11. **Evaluation harness** — отдельный процесс, который фиксирует dataset/index/
    model/config/code versions и формирует плоский JSON для кейсодержателя.

Командой также подготовлены Docling/dots.ocr, GPT-OSS, BGE-M3 и BGE reranker.
Это вспомогательная OCR/text-ветка, а не визуальный поиск. Граница и способ
сравнительной оценки зафиксированы в
[`docs/infrastructure/AI-SERVICES.md`](docs/infrastructure/AI-SERVICES.md).

## Контракты

### Оценочный ответ

```json
{"slug":"wine-slug"}
```

Точная семантика `not_found` для Bash-скрипта требует подтверждения у
кейсодержателя до заморозки API.

### Внутренний поисковый результат

Внутренний контракт должен содержать `request_id`, версии pipeline/index,
top-1/top-5 кандидатов, scores, margin, решение confidence policy, latency по
этапам и причину отказа. Он не обязан совпадать с публичным плоским endpoint.

### Карточка

Карточка связывается только по `slug` и содержит каталожные поля. Поисковый слой
не генерирует производителя, регион, сорт, рейтинг или описание.

### Идентичность и каталоги

`wine_family_id` отвечает на вопрос «какое это вино/кюве»,
`bottle_variant_id` — «какой точный винтаж/объём/вариант бутылки», а
`label_design_id` — «какое поколение внешнего вида». Связь с витриной хранится
отдельно как catalog membership конкретного snapshot.

Open-world библиотека не расширяет публичный контракт самовольно: внешний или
устаревший вариант может улучшать признаки, быть hard negative и объяснять
отказ, но `slug` возвращается только при подтверждённом current-catalog match.
Так библиотека помогает переживать обновления каталога и редизайн, не создавая
ложных ответов.

## Слои хранения

- Каталог и метаданные — реляционное хранилище либо воспроизводимый локальный
  snapshot.
- Визуальные признаки и индекс — immutable artifact с версией и manifest hash.
- Сырые изображения — локальный/закрытый контур, не Git.
- Манифесты и splits — версионируемые текстовые артефакты без закрытых URL и
  чувствительных данных.
- Нерешённые identity/origin задачи и сцены без полной разметки — per-source
  `review/needs_verification` и `review/needs_annotation`; media не копируются.
- Эксперименты — `runs/<date>-<name>/` с конфигом, метриками и выводом.

## Нефункциональные инварианты

- Модель загружается один раз на процесс, запросы ограничены по памяти и времени.
- Unit tests работают без GPU, сети и приватного датасета.
- Производительный прогон измеряет cold и warm path отдельно.
- Порядок top-K детерминирован при равных score.
- Индекс не строится из public/private test и не меняется во время оценки.
- Логи не содержат изображения, EXIF, токены и приватные каталожные поля.
- Декодирование изображений защищено от decompression bombs и некорректных
  форматов.

## Открытые решения, требующие данных

- Модель глобальных признаков и необходимость fine-tuning.
- Локальный matcher/reranker для near-duplicates.
- Польза OCR и набор допустимых полей для него.
- Тип индекса: in-memory exact, FAISS либо PostgreSQL/pgvector.
- Порог отказа и сценарий для неизвестного вина.
- Backend/frontend/CMS стек и граница встраивания в «Своё Вино».
- Дополнительная post-search функция.

Каждое принятое решение оформляется ADR после измеримого сравнения.
