## Что выбрать по уже полученным результатам

**CPU:** SO400M whole-view в FP32 ONNX Runtime, 6 потоков на Sigma. Все 316 полных
HTTP-запросов завершены вовремя; порядок всех ответов совпал с PyTorch. Это самый
практичный из полностью проверенных CPU-вариантов, но он уступает GPU-композициям
по качеству и не выполняет цель 3 секунды на каждом входе.

**GPU:** Qwen20 и ранее обученный адаптер Ромы оба дают 50/54 на сохранённых
кандидатах B. При настоящем лимите 10 секунд ответы теряются из-за времени.
У Roman20 пропуск дополнительной модели после 6 секунд базового поиска сократил
25 тайм-аутов до одного и дал 48/54. Это перспективный каскад для следующей
проверки на новых фото; ни один вариант пока не готов к безусловной замене TEST.

**Дешёвое улучшение:** нормализация смешанной кириллицы/латиницы в OCR исправила
два реальных фото без регрессий: 44 → 46/54. Больше моделей не всегда лучше:
LightGlue, постоянный второй CPU-кроп, чтение Qwen вместо OCR и простые правила
сорта/сладости не выиграли у соответствующих контролей.

## Что именно тестировали

Нового обучения нет. Адаптер Ромы обучен им ранее; его перенос отмечен отдельно.
Воспроизвести исходный поиск Ромы целиком нельзя: в handoff нет предшествующих
score/pool-файлов. Roman5 и Roman20 — два применения одного адаптера поверх нашего B.

```text
B / GPU:
фото → RT-DETR (бутылки) → SigLIP Base (центральное вино)
     → OWLv2 (этикетка)
     ├─ SO400M: целая выбранная цель → визуальные кандидаты
     ├─ SO400M: этикетка → визуальные кандидаты
     └─ PaddleOCR → текстовый поиск по всему каталогу
     → объединение рангов → Top20

CPU ORT6:
фото → выбор центрального вина
     ├─ бутылка найдена → кроп цели
     └─ нет бутылки → OWLv2-640 ищет этикетку
     → один SO400M FP32 ONNX-вектор → сравнение с готовым индексом

Qwen20:
свежий B Top20 → кроп запроса + фото/поля каждого кандидата
               → Qwen3-VL-Reranker-2B → новый порядок

Roman5 / Roman20:
свежий B Top20 + полное фото
  ├─ первые 5 → Qwen3.5-4B с адаптером Ромы → выбор
  └─ группы по 5 → промежуточные выборы → финальные 5 → выбор
  → исходные пороги и смесь с B
Deadline6: если B уже занял 6 секунд → вернуть свежий B без турнира

LightGlue:
этикетка + B Top20 → DISK-точки → LightGlue-пары
                  → геометрическая проверка → перестановка кандидатов
```

Для retrieval входом служит уже проверенный кроп. Ни один reranker не вернёт
товар, отсутствующий в Top20. OCR-поиск по всему каталогу может его добавить.

## Данные и честный знаменатель

- Frozen v2: 213 запросов — 141 graded service, 62 retrieval, 10 ungraded service.
- Организаторы: 103 файла, 100 уникальных SHA. Accuracy считаем по **54 exact**;
  42 unresolved, 3 ambiguous и один подтверждённый OOD — отдельно.
- 54 exact — 37 SKU и 42 группы сцен. Между наборами 12 одинаковых SHA;
  всего 300 уникальных изображений в 316 запросах.
- Retrieval v2: 50 аугментаций и 12 AI, независимых реальных фото нет.
  Service graded: 32 real, 70 augmentation, 39 AI.
- Каталог: 2103 ID, 2060 разрешённых визуальных эталонов, 43 недоступных.
  20 конфликтных фото остаются исключёнными. Исходный CSV, frozen v2 и gold не изменены.
- Пять известных конфликтов reference/упаковки сохраняются в основном знаменателе.
  На остальных 49 B даёт 40/49, Qwen20/Roman20 — по 46/49; на конфликтных — по 4/5.

Это повторно используемый development-набор с локально проверенными ответами,
а не официальный answer key и не независимый holdout. Unresolved не означает OOD.
На inference-поды не передавали gold. Подробные ответы и спорные случаи вне Git/web-root.

## Что отклонено и почему

- **Динамический INT8 запроса с FP32-индексом:** все 213 frozen вовремя,
  p50/p95 2,03/3,93 с, но service 65/141, retrieval 35/43/43 из 62.
  Ноль исправлений, 45 новых service-ошибок и 21 retrieval Top1-ошибка.
  Organizer не запускали. Это не вывод про все виды INT8 или согласованный новый индекс.
  Начальные тайминги пересеклись с копированием артефактов на Sigma.
- **Qwen с публичными категорией/сладостью витрины:** 277/316 вовремя, 39 timeout;
  service 111/141, retrieval 61/62, real 33/54. На общих 39 timely exact-фото
  baseline 35 верных, website 33: ноль исправлений, две регрессии. Источник поля
  проверен для 2029 карточек; 69 отсутствующих и 5 конфликтных оставлены пустыми.
  Большую разницу задержек не приписываем самим полям: разные запуски вариативны.
  Три duplicate SHA дали разные timeout-исходы; unique-score берёт первое появление,
  не лучший повтор. Все файловые ответы остаются в raw.
- **CPU Base224:** real 29/54 вместо 39/54. Компактность не компенсирует потерю качества.
- **Постоянный второй CPU-кроп:** только 203/213 frozen вовремя, service 98/141,
  retrieval 54/62. 0 исправлений / 12 регрессий service; organizer после этого не запускали.
- **Постоянный PaddleOCR на CPU:** по шесть timeout в frozen и organizer, real 28/54.
- **OCR1280 перед Roman20:** 35 timeout вместо 25, real 39/54 вместо 45/54 strict.
- **Qwen OMP1 + offline flags:** 27 timeout вместо 9; на 289 общих успешных запросах
  одинаковые ответы. Изменились несколько настроек, чистой причинности не утверждаем.
- **Qwen OCR:** p95 только читающей модели на L4 9,88 с; 11/288 вызовов >10 с,
  real +6 исправлений и −5 регрессий. Для обычного пути слишком дорого по времени.
- **Имена файлов эталонов в lexical-поиске:** real 41/54; с нормализацией 44/54,
  ниже 46/54 без имени. Публичные поля витрины проверяются отдельно.
- **Правило буквального сорта:** real 44/54, прироста нет. Правило сладости — 43/54,
  одна регрессия. Не добавляем частные исключения под известный ошибочный кадр.
- **MKLDNN-проба Paddle:** быстрый ответ оказался исключением OCR и пустым текстом;
  это сбой компонента, не ускорение распознавания. Нужна видимость degraded-режима.

## Что остаётся сломанным

1. **Недостаточно информации:** все основные варианты 0/10 соответствующих service-кейсов.
   Улучшение ранга товара не исправляет поведение. Нужна отдельная политика качества
   видимых свидетельств, с проверкой ложных отказов на положительных кадрах.
2. **Товара нет в каталоге:** 0/1 правильных отказов на подтверждённом real OOD.
   Frozen 19/22 no-match не доказывает устойчивость на неизвестных винах.
   По одному OOD нельзя калибровать порог; 42 unresolved нельзя записать в отрицательные.
3. **Неправильная центральная цель:** общий тяжёлый кейс теряет товар ещё до Top20.
   Нужны выбор центрального вина, путь отдельной этикетки и OCR только нужной области.
4. **Соседние варианты линейки:** сладость, название и оформление; невидимые детали
   нельзя достоверно угадать. Часть каталожных фотографий общая между карточками.
5. **Независимость проверки:** новые real-положительные/отрицательные сцены нужны раньше
   следующего перебора десятков комбинаций на тех же 54 фото.

## Проверки контракта и границы результата

Неизменённый скрипт организаторов через SSH-туннель: CPU ORT6 12/12, максимум 5,53 с;
исходный Roman20 4/6 ответов и 2 timeout. Это sample, а не полный запуск всех фото
через публичный TLS ingress. Два одновременных CPU-клиента: один 200 за 4,76 с,
второй 503 busy за 57 мс; следующий запрос 200 за 3,26 с. Один inference-slot.
GPU-нагрузка несколькими клиентами отдельно не доказана.

В Qwen/Roman заменена проекция Conv3d на F.linear с теми же весами, без обучения;
BF16 не побитово идентичен. Результаты относятся к зафиксированному runtime-варианту.
Qwen microbatch4 менял ранги и отклонён. Точные SHA-пересечения с переданными
Roman train/validation не найдены; отсутствие near-duplicates этим не доказано.

## Дальнейший план

1. Закрепить два кандидата: CPU ORT6 и GPU Roman20 deadline6; Roman5 оставить более быстрым GPU-компромиссом. INT8 и website-поля отклонены
   по полным контрольным прогонам. TEST сейчас не заменять.
2. Собрать небольшой независимый real holdout: exact, неизвестные вина, недостаточная
   информация, отдельная/частичная этикетка, центральное вино среди других объектов.
   Gold подтверждать доказательствами; конфликты отдельно, без удобного исключения ошибок.
3. Проверить выбор цели и режимы отказа раздельно от ранжирования. Исправлять общую
   причину, затем весь frozen + real, со счётом новых ложных отказов и регрессий.
4. Для CPU проверить редкую адресную label/OCR-ветку вместо второго вида на каждом запросе.
   Для GPU проверить budget-aware каскад на holdout и полный сетевой SLA под нагрузкой.
5. Только затем решать, нужен ли новый этап обучения. Текущие результаты показывают
   потенциал готовых методов; обучение не исправит ошибочный контракт и плохой gold.
