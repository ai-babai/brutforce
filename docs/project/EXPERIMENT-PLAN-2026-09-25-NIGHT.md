## Цель и исходная реальность

Предпочтение Макса — полностью локальный inference на Sigma CPU без GPU и внешнего model API.
GPU остаётся полноценным кандидатом, если CPU существенно уступает по качеству/времени.
Допустимый размен качества на стоимость пока не согласован: представить оба результата,
не объявлять CPU победителем только из-за отсутствия GPU.

- Sigma: 8 vCPU KVM, host CPU AMD EPYC 9654, 15 GiB RAM; это не 8 выделенных физических ядер.
- CPU whole-only: 39/54 exact Top1, 50/54 Top5/20; service 106/141, retrieval 56/62 Top1.
  Пять реальных timeout из 213 frozen запросов; успешные ответы не заменяют полный знаменатель.
- GPU B: 44/54 Top1, 51/54 Top5, 53/54 Top20; service 114/141, retrieval 57/62 Top1.
  Предыдущий контроль: 42/49/51. GPU p95 5,50 с — loopback, не внешний SLA.
- 100 уникальных organizer-фото: 54 exact, 42 unresolved, 3 ambiguous, 1 подтверждённый OOD.
  103 файла содержат три точных дубля. В accuracy каждый оригинал считается один раз.
- 16 новых Roman-кандидатов ещё без gold; они не закрытый независимый тест его адаптеров.

## Требования и независимость оценки

ТЗ: CV обязателен; GPU предусмотрен, CPU допустим при отсутствии GPU; цель ответа до 3 с.
Original script: multipart image, один slug, connect-timeout 5 с, весь запрос max-time 10 с.
Скрипт не считает F1 и не определяет, когда null является правильным отказом.
Не заменять конкурсный ответ похожим товаром под видом точного; аналоги — отдельное поведение приложения.
Ни один опыт не меняет согласованный контракт или политику отказа молча.

- Входы: frozen v2 (213, включая 141 graded service, 62 retrieval и 10 ungraded) и все 100 organizer-оригиналов.
- Exact метрики только для подтверждённых ответов; ambiguous/unresolved отдельно; OOD не смешивать с exact.
- Для service подавать полный кадр; для retrieval — предусмотренный тестом проверенный вход.
- Gold доступен только evaluator после сохранения predictions. Не вставлять правильный ответ в пул.
- Сохранять каталог2103, reference hashes, image/capture IDs, preprocessing, model/config SHA и кандидатов.
- Rerank на фиксированном пуле не меняет Recall@20; новый pool/crop/index получает отдельный run ID.
- Все timeout, missing reference и unsupported случаи остаются в знаменателе или явно помечены ungraded.
- Локализацию оценивать только при подтверждённой целевой области; не выдумывать недостающую разметку.
- Roman train/validation, AI и реальные сцены — отдельные срезы. Test680/Field89 не открывать для подбора.

### N1. CPU — главный практический поток, GPT-6 Sol

```text
фото → RT-DETR / существующая область → SigLIP2 → точный поиск по индексу → slug
                                           + отдельно проверяемый PaddleOCR
```

1. Воспроизвести current whole-only; найти время decode/detect/embed/OCR/search и причины 5 timeout.
2. C1: те же веса/предсказания, оптимизация исполнения: inference mode, потоки,
   отсутствие повторной загрузки, ограниченная память; сравнить PyTorch и экспорт если он оправдан.
3. C2: один компактный кандидат — SigLIP2 Base-224 с новым согласованным индексом.
   Сначала только замена энкодера, затем отдельно whole+label; не приписывать смешанные изменения одному фактору.
4. PaddleOCR-only контроль, затем победитель C1/C2 + OCR. Текстовый поиск добавляет кандидатов самостоятельно.
5. INT8 только при нехватке скорости: отдельный профиль, калибровка без тестовых запросов,
   проверка соседей и качества после квантования. Не тратить ночь на неработающий exporter.

Настоящие финальные замеры на Sigma с зафиксированными CPU/RAM лимитами, один benchmark за раз.
CPU RunPod не является заменой Sigma-замеру. Другие сервисы не останавливать, shared load записывать.
Готово: полный service/retrieval/organizer прогон контроля и CPU-финалиста, таблица точность–latency–RAM.
Промежуточные абляции сначала на фиксированном диагностическом subset; все 5 проблемных кейсов видны.
Subset не объявлять полным сравнением и не переносить его проценты на весь набор.

### N2. Цель и текстовые доказательства, GPT-6 Sol

```text
фото → центральное вино / label-only → признаки только этой цели
     → B: whole + label + OCR → Top20 → проверка видимых надписей → slug
```

Разобрать весь остаток ошибок B, а не только старые девять примеров.
E1: на фиксированном B Top20 сопоставить уверенно прочитанные производителя/линейку/вариант с карточками.
При неизвестном поле сохранять порядок. Не путать сухое/полусухое, год основания/урожая, сорт/аромат.
E2 отдельно: привязать OCR к цели, проверить label-only и неоднозначную центральную цель.
Составной visual context сохранить как отдельный вид; не смешивать тексты соседей.
Если качество упирается именно в чтение, короткий Qwen-reader отдельной абляцией, без списка кандидатов в prompt.
Контроль E1 без новых правил и контроль E2 без новой маршрутизации обязательны.

Готово: причины исправлений/регрессий, выигрыш по разным SKU/сценам, нет подстановок по ID конкретного вина.

### N3. Один тяжёлый конкурент, GPT-6 Sol; условная GPU-ветка

```text
B Top20 + изображение цели + эталон/поля каждого кандидата
  → Qwen3-VL-Reranker-2B → новый порядок → slug
```

R0 — B; R1 — только Qwen reranker; R2 — R1 + проверка полей E1, только после отдельных контролей.
Один закреплённый prompt, разрешение и revision; начать с инженерного sample без выбора по gold.
Первый полный опыт без раннего выхода; microbatch проверить против batch-1 scores.
Сравнение на всех подходящих запросах, остальные сохраняют явную причину/контрольный fallback.
Промежуточный кеш разрешён для качества, запрещён для выдачи времени полного live inference.
Если нет полезного прироста или исполнение заведомо не помещается в бюджет — завершить ветку.
DISK+LightGlue либо DINO — только замена остановленного опыта при конкретной причине, не обязательный турнир.

### N4. Два решения Романа, отдельный GPT-6 Sol и до одного отдельного pod

1. **Roman-5:** `fullframe-qlora-lr1e-4-v1` — Qwen3.5-4B с переданным адаптером выбирает из пяти.
2. **Roman-20:** `candidate20-fullframe-v1` — тот же адаптер сравнивает группы из Top20, затем финальную пятёрку.
   Это две архитектуры с одними обученными весами, не две независимо обученные модели.

```text
наш зафиксированный поиск → те же Top20
  ├─ первые 5 → base Qwen / base + Roman adapter → выбор
  └─ группы из 20 → последовательные сравнения → финальные 5 → выбор
```

Контроли: без judge; pinned base без LoRA; тот же base с адаптером.
Для RR20 отделить увеличение пула/числа вызовов от изменения весов.
Base: `Qwen/Qwen3.5-4B@851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`.
Сохранить переданные prompt/fusion/quantization; не оптимизировать по нашим gold до исходного прогона.
Честно подписать перенос на наш поиск как композицию, а не полное воспроизведение Роминого cascade590.
Параллельно проверить восстановимость исходного поиска Ромы. При полном комплекте — отдельный end-to-end профиль.
Если недостаёт ancestor-артефактов, записать конкретные пробелы, не заменять их кешем старых ответов.
Clean v4/v7 с выбранным alpha=0 не выдавать за два разных победивших решения.

Setup gate максимум 120 минут: совместимость, веса/входы, два smoke, оценка длительности полного прогона.
Цель — оба варианта на всех frozen/organizer входах, включая провалы Top5 и каталоговые пробелы.
Приоритет: Roman-5 полный, затем Roman-20 полный. RR20 smoke выполнить рано, чтобы оценить оставшийся бюджет.
Если полный прогон не вмещается, сохранить частичность и завершить ресурсы; не объявлять выборку полным тестом.

## Приёмка, выбор и остановка

1. Для каждого профиля: ASCII-архитектура, точные веса/конфиг, raw predictions, отдельные submissions service/retrieval.
2. Качество: Top1/5/20, MRR, service pass, fixed/broken по SKU и capture; реальные/AI отдельно.
   Все 54 exact остаются в знаменателе; условная точность judge при gold в Top5 — лишь дополнительная метрика.
3. Техническая оптимизация C1: одинаковые итоговые ответы; любое изменение ранга — отдельный качественный опыт.
4. Новый тяжёлый компонент: ориентир net +2 различных SKU/групп относительно актуального контроля,
   полный список broken, без критического ухудшения negative/target сценариев. Это критерий отбора, не статистическая гарантия.
5. Скорость: batch-1 p50/p95/p99/max, холодный старт отдельно, полный внешний original script без query-result cache.
   Цель ТЗ ≤3 с; практический запас p95 ≤8 с и 0 наблюдённых timeout при 10 с на последовательном полном прогоне.
   Указать долю >3 с, все failures и зависимость от размера upload; успех не гарантирует произвольную сеть.
6. Нагрузка отдельно: пара одновременных клиентов, queue/busy/cancellation; не прятать быстрый 503 в успешный SLA.
7. CPU выбирается по близости к лучшему качеству и latency; существенный размен представить Максу явно.
8. STOP: 120 минут setup без working inference; 45 минут без новой гипотезы по одной ошибке;
   повтор старых отрицательных опытов; отсутствует наблюдаемый признак; рост только на дублях/AI; перерасход/дедлайн.
