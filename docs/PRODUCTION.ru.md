## Где исходники

- [`apps/vision/c16/`](../apps/vision/c16/README.md) — 42 Python-файла действующего
  C16, перенесённые с сервера без изменения байтов, и его frozen metadata.
- [`apps/vision/boost/`](../apps/vision/boost/) — исходный SIMPLE84 retrieval,
  его неизменные policy и runtime. C16 наблюдает эти вычисления и уточняет порядок
  кандидатов по связанным визуальным и OCR-свидетельствам.
- [`apps/vision/parent/`](../apps/vision/parent/) — 16 прежних модулей модели;
  все сверены с сервером. Их наличие не означает активный старый F8 HTTP-профиль.
- [`apps/api/uploads.go`](../apps/api/uploads.go) — реальная серверная правка:
  чтение мобильной загрузки до 90 секунд, запись ответа до 120 секунд;
  сетевой таймаут возвращает `408 upload_timeout`, а не ошибку типа изображения.
  Ограничения размера и числа загрузок сохранены.
- [`apps/web/src/production-scanner.css`](../apps/web/src/production-scanner.css) —
  боевой индикатор сканирования, включая режим reduced motion.

Текущий frontend JS пересобран из Git и **побайтово совпал** с обслуживаемым
`index-CnGrfq7m.js`: SHA `43f6f92608c71125fd27c673d2fbee987bc94a61cd978aa9b8917e7150695ee6`.
На сервере CSS-индикатор подключён отдельным файлом; в исходниках он импортируется
после основного CSS. Имена и байты объединённого CSS после сборки отличаются.

## Что было неверно

`/release.json` продолжает показывать `b8e71fc`, а прежний release controller —
ещё более старый кандидат с F8/A2. Эти записи не описывают эффективные unit overrides.
Живой API использует отдельный исправленный бинарник и vision `127.0.0.1:8137`.
Поэтому состояние установлено по `/proc`, `/healthz` и контрольным суммам файлов,
а не по старому указателю выпуска. Исправление серверных release receipts требует
отдельной серверной задачи; при этой синхронизации они сохранены как есть.

## Проверка checkout

Из корня репозитория, без загрузки моделей и запуска сервисов:

```sh
python3 scripts/production-vision.py
```

Результат отдельно сообщает `sources_verified` и `assets_verified`.
Без `--data-root` проверяется только код. Наличие исходников не заменяет данные модели.

## Внешние данные и запуск

Суммарно закреплено около 4 ГБ внешних файлов. Получать их следует у владельца
действующей модели; старый публичный F8-комплект не является C16-комплектом.
Веса, каталоги, производные галереи, фотографии и секреты в Git не включаются.
Каждая строка `externalAssets` задаёт путь относительно отдельного `DATA_ROOT`:

```text
DATA_ROOT/
  onnx/             vision.onnx, vision.onnx.data и processor/
  index/            Batch32 index.npz и index-info.json
  catalog/          catalog-bundle.json
  models/hub/       закреплённые HF snapshots детектора и вспомогательных моделей
  metadata/         catalog-attributes.json и CANDIDATE-FREEZE.json
  c16/assets/       восемь точных derived-gallery файлов
  ocr/              tesseract, eng.traineddata, rus.traineddata
  overlay/          organizer-slugs.json
  recommendations/ index.json с текущей совместимостью C16
```

`ocr/tesseract` — точный Linux-бинарник сервера, а не произвольная версия из apt.
Его библиотеки, модельные зависимости и архитектура хоста тоже должны быть совместимы.
Публичная ссылка на старые веса не подтверждает права распространения новых данных.
Полный `DATA_ROOT` проверяется без запуска:

```sh
python3 scripts/production-vision.py --data-root /absolute/path/to/c16-data
```

Для явного запуска модели на Linux с Python 3.12 и версиями из
`pythonPackages` манифеста:

```sh
python3.12 scripts/production-vision.py \
  --data-root /absolute/path/to/c16-data \
  --runtime /absolute/path/to/new-private-runtime --serve
```

Скрипт проверяет код и данные, создаёт **новый** runtime вне checkout,
переносит только машинные привязки путей и запускает неизменный `serve_v7.py`
на loopback `8137`. Исходники inference не переписываются. Данные не скачиваются,
systemd не меняется. Прежние квитанции активации Sigma не копируются: новый запуск
не должен выдавать себя за квалифицированный и активированный прод.
Workflow traces содержат частные диагностические сведения и остаются в этом runtime.

Для полного приложения нужны отдельно PostgreSQL, display package/media,
приватное хранилище uploads и локальные credentials. API собирается из `apps/api`,
UI — из `apps/web`. В существующей конфигурации API задайте
`VISION_SERVICE_URL=http://127.0.0.1:8137`, версии из `production.json`,
путь и SHA allowlist, путь и SHA индекса рекомендаций. Базу и пользовательские
файлы из продакшена для этого не копировать. Контракты:
[vision](../contracts/vision-serving.md), [uploads](../contracts/photo-upload.md),
[каталог](../contracts/catalog-display.md).
