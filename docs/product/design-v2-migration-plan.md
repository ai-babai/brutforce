# Переход приложения на выбранный дизайн 2.0

Дата: 20.09.2026. Статус: анализ и предложение, реализация не начата.

## Срез источников

- Приложение: `codex/behavior-demo`, `15354a3`, релиз v5.10; последний отчёт — 87 кейсов. Это исторический результат, не повторный прогон при анализе.
- Целевой дизайн: `design/wine-ux-v2/selected-edition.md` и `published-version.json` в `codex/camera-viewport` (`ae01d59`); опубликованный контент — `29874e7`, https://reps.maks.dzap.pw/v2/#flows.
- `design.js`, `v2.js`, `navigation-v2.js` публичной версии сверены с `29874e7`: совпадают побайтно.
- Старая редакция `/v2/previous/` и исследование `wine-after-scan` не являются автоматически новыми требованиями. В частности, компас вкуса, рейтинги и торговые функции в этот перенос не включаем.
- Макет содержит симуляции камеры, галереи, поиска и сети. Переносим оформление и согласованные переходы, сохраняя настоящие возможности приложения.

## Главный вывод

Это миграция визуальной системы **и нескольких переходов состояния**, а не замена CSS. Go API, защита загрузок, приватное хранилище фото, PWA и быстрый runner сохраняются. Распознаватель для конкурсного API по-прежнему не подключён; дизайн этого не исправляет.

## Карта изменений

| Область | Сейчас → целевая версия | Что проверить |
|---|---|---|
| Главная | Наклонённая бутылка → выбранный 2D пёс с бутылкой, новый логотип и поверхности | Иллюстрация не закрывает текст/кнопки; на 320 px видны действия; alt; ошибки загрузки ассета |
| Отмена | Отдельный `cancelled` → главная с «Продолжить поиск» и просмотром сохранённого снимка | Abort запросов/таймера; поздний ответ не меняет экран; повтор использует тот же File или receipt |
| Просмотр снимка | Модальное увеличение → представление фото с возвратом к месту входа | Из кандидатов, карточки, ошибки сети и главной возвращаемся корректно; завершившийся запрос не теряется |
| Ручной поиск | Каталог сразу + общий back на главную → пустое состояние, запрос, результат и возврат в запрос | Enter/кнопка; hit/miss; исходный запрос и кандидаты сохранены; нет выдуманного пользовательского фото |

| Плохое фото | `badphoto` означает неверный MIME/размер | Не превращать это в утверждение о блике/размытости: для оценки качества изображения нужен отдельный сигнал |
| Маскот | Отсутствует → главная, поиск/ожидание, нет совпадения, пустой ручной поиск, ошибка сети | Не появляется поверх камеры, разрешений, пользовательского фото, кандидатов и данных вина |
| Карточка | Старые карточки/вкладки → новая композиция, факты и действия | Нет данных — явно «Нет данных»; идентичность вина; вкладки; источник; сохранение/удаление |

## Что делать с существующими проверками

- Сохранить без ослабления API-001…019, EVAL-001…009, SEC-001…009, REPORT-001…003 и UI-025: редизайн не меняет контракт или защиту. Изменять их только при реальном изменении соответствующего поведения.
- UI-005: переписать ожидаемый экран после отмены; сохранить проверку отмены, снимка и защиты от позднего ответа. ID сохраняет смысл «отмена без потери контекста».
- UI-004: проверить остановку ожидания и отсутствие перехода по запоздалому ответу после отмены. UI-010 имеет пробел: текущая проверка преимущественно проверяет неверный `selectedId`, а не успешный повтор после ошибки; добавить полноценный цикл ошибка → повтор → результат.
- UI-006/007/008/009/010 и проверки исходного фото: дополнить переходами назад, сохранением запроса, повтором и отсутствием фото в текстовом поиске. Не ограничиваться проверкой надписи.
- UI-011: оставить проверку некорректного файла; не выдавать её за оценку качества фотографии.
- UI-016…024: сохранить полезные свойства каталога, сохранённого и кнопок; конкретные ожидания нижней панели зависят от решения о навигации.
- DESIGN-001/002/006/009/013/014/018/019/020: сверить и обновить размеры, цвета, шрифтовую иерархию и компоненты по финальному CSS каскаду v2. Нельзя брать первое найденное значение из старого `design.css`: макет имеет несколько слоёв переопределений.
- DESIGN-021: старое требование к наклону и обрезке бутылки снимается с новой версии. Исторические результаты не менять; добавить новый кейс композиции маскота, не переименовывать старый зелёный результат в новое доказательство.
- DESIGN-003/004/005/007/008/010/011/012/015/016/017: сохранить смысл — локальные шрифты, адаптивность, отсутствие отладочных контролов, доступность действий, безопасная камера/затвор и границы экрана. Числовые параметры менять только по целевому дизайну.
- Новые IDs выделить для возобновления с главной, контекстного возврата, гонки preview/retry и правил размещения маскота. Не дублировать существующие кейсы только ради новой картинки.

Предлагаемые новые сценарии (номера назначить при реализации): просмотр фото → точное место входа; повтор после отключения сети с тем же снимком; просмотр фото во время повтора не восстанавливает старую ошибку; текстовый поиск сохраняет запрос и не показывает выдуманный снимок; выбор кандидата сохраняется при возврате; пересъёмка позволяет выйти из ошибки плохого кадра. Отмену расширяем в UI-004/005, без второго одинакового кейса.

## Данные и API

Для навигации и маскота миграция БД/API не нужна. Не переносить из макета выбор вина по году, условие «запрос содержит демо» и таймер, имитирующий успех.

В карточке v2 есть тип/цвет/сахар, регион и крепость, которых нет в текущем `Candidate`. Минимальная миграция: optional-поля контракта и согласованные синтетические fixtures; отсутствующие значения отображаются явно. Конкретную ссылку источника показывать только при её наличии. Это совместимое расширение `/v1`, не повод заводить `/v2` API из-за номера дизайна.

Сохранённое сейчас лежит в `wine-demo-saved-v1` как копии карточек. Старые записи без новых optional-полей должны читаться; нельзя очищать список из-за редизайна. Если форма хранения реально меняется — добавить небольшой явный преобразователь и тест старого формата.

## Порядок перехода

1. **Зафиксировать цель и решения.** Закрепить `29874e7`, список экранов и выбранные ассеты. Согласовать навигацию/сохранённое и начальное состояние ручного поиска. Макет — источник оформления, утверждённые кейсы — источник поведения.
2. **Сначала переходы и красные тесты.** Уточнить GWT отмены, возобновления, back, preview/retry, hit/miss и исправления вина. Сделать маленькую модель контекста: источник перехода, запрос, выбранное вино, снимок/receipt, активный запрос. Достаточно локального reducer/типов; отдельный workflow framework не нужен.
3. **Перенести визуальную систему.** Общие токены, локальные ассеты, кнопки, поля, карточки и поверхности; затем экраны. Не копировать весь прототип и его report-навигацию в приложение. Удалить заменённые CSS-правила вместо очередного большого слоя overrides.
4. **Проверить сохраняемые возможности.** Реальная камера/галерея, загрузка, PWA и обычный браузер, сохранённое, повтор запроса, лимиты и конкурсный адаптер. Если добавили данные карточки — обновить схему, Go/TS и контрактные тесты вместе.
5. **Проверить и передать.** Быстрые тесты прямых переходов/компонентов; отдельное браузерное ревью 320×568, 390×844, 844×390 и широкий экран, с панелями браузера и без них. Затем новая колонка отчёта, коммит/PR с указанным SHA дизайна; публикация только в рамках отдельного согласованного этапа.

## Границы доказательств

Быстрые тесты проверяют настоящий reducer/React-компоненты и обработку API; сеть/камера подменяются только на границах. Они не доказывают реальную геометрию. CSS-контракт может обнаружить потерю токена, но пересечения, читаемость и доступный затвор проверяются браузером. Playwright не нужен в каждом цикле генерации. Тесты статического макета — список полезных сценариев, а не готовые тесты приложения.

## Решения перед реализацией

1. Предлагаю сохранить нижнюю навигацию и «Сохранённое», адаптировать их к v2, а не удалять уже работающие пути.
2. Предлагаю на пустом ручном поиске показать маскота/подсказку как в v2, но оставить вход в существующий каталог. При вводе — реальные результаты нашего поиска, не логика симулятора.
3. «Какое вино перед вами?» — ранее высказанная правка Макса; и код, и новый макет всё ещё содержат «Что за вино…». Зафиксировать согласованный текст в спеках при переносе.
4. Сохранить ранее согласованную рамку телефона на широком экране (DESIGN-015/016), пока нет явного решения её убрать. Оформление каталога макетов и его навигацию в продукт не переносить. Для DESIGN-004 добавить 320 px, сохранив полезные существующие размеры проверок.

Никаких изменений приложения, дизайна или live-сервисов при этом анализе не выполнено.
