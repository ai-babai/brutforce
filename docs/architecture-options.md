# Варианты архитектуры

Статус: предложение для обсуждения, 2026-09-15. Подробное ТЗ и датасет пока не проверены; предложения опираются на публичную карточку и исследование от 14 сентября.

Попытка повторного чтения в Chrome 15 сентября остановилась на блокировке Mac. Это ограничение проверки, а не свидетельство отсутствия ТЗ на сайте.

## Что известно

Публичная задача РСХБ требует найти по фотографии нужную карточку в массиве вин «Свое Вино». Схема каталога, метрика, ограничения запуска и разделение винтажей из неё не следуют.
Источник: https://i.moscow/hackaton/lct/3a9c0c2e86184425bd73d4cedbf6565a.

Пользователь выбрал винный трек, название команды «Брютфорс», приватный монорепозиторий. Доступны Android-телефоны. Агентная разработка не означает, что продукту нужен мультиагентный runtime.

## Варианты

### A. Мобильный веб-клиент + один Python-сервис — рекомендуемый старт

Клиент снимает/загружает фотографию. Сервис содержит API, импорт каталога и модуль поиска. OCR и визуальный поиск сначала сравниваются раздельно, затем объединяются при подтверждённой пользе.

Плюсы: один серверный процесс, общий код поиска для API и оценки, мало инфраструктуры. Минусы: при серверном распознавании нужен интернет; возможности камеры ограничены браузером.

Возможное дерево после согласования:

```text
apps/web/                мобильный интерфейс / PWA
backend/src/brutfors/    API, catalog, recognition
evaluation/             описание наборов, метрик и компактные отчёты
contracts/              канонические экспортированные схемы и описания
docs/                   решения и запуск
```

У каждой области будут AGENTS.md и контракт. Внутренним модулям достаточно ясных Python-интерфейсов и документации; отдельный HTTP между ними не нужен. Постоянные тесты и оценочные скрипты — после отдельного разрешения, а не часть текущей заготовки.

### B. Веб-клиент + API + отдельный сервис распознавания

Полезно, если inference требует отдельной GPU-машины или строгой изоляции зависимостей. Добавляет сетевой контракт, развёртывание и обработку недоступности модели. Выбирать по подтверждённой потребности, а не ради архитектуры.

### C. Android APK + сервер поиска

Полезно, если ТЗ требует APK или нужна камера, которой недостаточно в браузере. Отдельная сборка и проверка Android-клиента. На качество серверного поиска выбор APK сам по себе не влияет. Полностью офлайн-вариант существенно меняет ограничения моделей и не включён в стартовый план.

## Поиск и проверка

1. Проверить данные: изображения, число карточек, дубли, год/объём, единица правильного ответа.
2. Построить текстовый baseline OCR → поиск по полям каталога.
3. Построить визуальный baseline → ближайшие эталонные изображения.
4. На одинаковых независимых запросах сравнить методы, ошибки и задержку. Запросы должны быть отличны от эталонных фотографий, но известный товар должен присутствовать в галерее.
5. Объединить кандидатов и сигналы; усложнять только после измеримого улучшения.
6. Подключить камеру, выдачу карточки и сценарий неоднозначности, допустимый ТЗ.

Не предполагаем необходимость дообучения, векторной БД, очередей, Kubernetes или LLM-сомелье до появления соответствующих данных и требований.

## Что нужно выяснить до реализации

- Метрика: точная карточка или семейство; top-1/top-k; допустимость отказа.
- Наличие эталонных изображений и настоящих телефонных фото, правила винтажей.
- Целевое железо, внешние API, интернет, лицензии pretrained-моделей.
- Требование PWA/APK и формат сдачи/интеграции.

После этого можно согласовать вариант A или обоснованную альтернативу, конкретные контракты и первый сквозной этап. Этот документ не запускает реализацию автоматически.
