# Запуск и обслуживание · 28.09.2026

Основной runbook для локального демо и планируемого CPU-профиля F8. [English entry](RUNBOOK.en.md) ссылается на те же команды. Описание серверного выпуска и approval — [deploy/PIPELINE.md](../deploy/PIPELINE.md). В текущей ветке полного F8 asset bundle и согласованной команды выдачи эксперту пока нет: **приведённый ниже подготовительный контракт не является пройденным clean-clone запуском**.

## Предварительные условия

- Локальное синтетическое демо: Go 1.23, Node.js 22, npm; любая поддерживаемая ими ОС. Без базы и весов. Храните реальные фото в непубличной папке.
- Реальный F8 CPU: Linux x86-64, Docker/Compose после интеграции упаковки **или** настроенный отдельно Go/API, PostgreSQL и vision runtime; достаточно свободной памяти для модели и индекса (точный проверенный лимит для чистого Linux запуска pending). CPU-сервис должен прогреться до readiness до первой оценки; предыдущая cold-load проба была 15,453 с.
- Обязательные внешние bytes и права на их получение: код F8 с parent imports, веса/детектор, SO400M/препроцессинг, OCR lexicon, индекс и metadata, allowlist slug, mapping витрины, media каталога, recommendation index и все зависимые версии. Нельзя скопировать только шесть SHA из [f8-runtime.json](../deploy/f8-runtime.json) и считать сборку полной.

## Локальное демо без ML

Из корня клона выполните ровно [команды README](../README.md#быстрый-запуск) в двух терминалах. Проба liveness: `curl --fail http://127.0.0.1:8097/v1/health`. Это не readiness БД или F8. `POST /v1/eval/predict` без F8 предсказуемо отвечает 503; никогда не использовать демо как оценку точности. Остановить оба процесса Ctrl-C. Папка `local-uploads/` игнорируется Git, но её содержимое удаляет только владелец данных.

Быстрые локальные проверки (после установки npm-зависимостей):

```sh
cd apps/api && go test -count=1 ./...
cd ../web && npm test && npm run build
```

От корня репозитория можно запускать `node scripts/run-fast-checks.mjs`; он создаёт историю отчётов, а не доказывает работу F8 или реальной камеры. Для SQL-интеграции нужен выделенный тестовый PostgreSQL и отдельные runtime/migration credentials; [правила БД](../contracts/database.md). Не направляйте миграции на чужую/production БД.

## Полный CPU-профиль F8

**Приёмка получения assets pending.** Соседняя ветка упаковки готовит `deploy/compose.yaml`, `deploy/assets/f8-cpu.json`, `scripts/asset-bundle.py` с `verify|export` и явной operator source-map и `scripts/docker-local.sh` с `prepare|up|down|smoke`. После слияния проверить справку скриптов, полное покрытие SHA, права и работоспособность на чистом Linux clone до объявления команд рабочими. Эксперт не должен зависеть от личных Mac-путей или скрытого ручного копирования с Sigma. При отсутствии разрешённого канала выдачи bundle воспроизводимость остаётся pending.

Согласованные имена входов упаковки: `ASSET_DIR` (проверенный F8 bundle), `CATALOG_PACKAGE_DIR` (проверенный импорт), `CATALOG_VERSION`, `CATALOG_MEDIA_DIR`; локальный runtime env файл содержит DB credentials и другие секреты **только вне Git**. Не записывайте их в CLI-аргументы, Docker layers, Actions artifacts или эту инструкцию. Версии assets и каталога фиксируются отдельно; запуск при mismatch должен завершаться ошибкой, а не использовать синтетику.

После получения пакета и интеграции скриптов порядок приёмки: (1) проверить manifests/SHA и законность доступа; (2) подготовить отдельную локальную БД и применить миграции migration-role (`go run ./cmd/catalog-migrate` из `apps/api`); (3) dry-run и затем разрешённый импорт display-каталога [по API-инструкции](../apps/api/README.md#be-045-реальный-каталог); (4) запустить и дождаться готовности vision и БД; (5) выполнить known-answer запрос и сверить конкретный slug и существующую карточку; (6) остановить только локально созданные процессы. Правило rollback: сохранить версии каталога/assets и DB snapshot; не делать `down/reset` постоянных данных. Точные Docker-команды, проверенные env examples и ожидаемые output будут вставлены после получения исполняемых файлов Sol B.

Контрольный конкурсный запрос к **уже работающему реальному** API с разрешённым локальным фото (не использовать в демо без F8):

```sh
curl --fail-with-body --max-time 10 -F "image=@/path/to/approved-sample.jpg" http://127.0.0.1:8097/v1/eval/predict
```

Ожидается HTTP 200/201 и JSON с одним непустым `slug`, равным известному gold для фото; один корректный JSON не доказывает accuracy. В продукте `POST /v1/photos` принимает поле `photo`, затем `POST /v1/search` принимает JSON с `photoId` и выдаёт существующие карточки. [Контракт](../contracts/vision-serving.md). Не передавайте личные фото в публикации, PR и логах.

## Обновление, PROD и откат

Публичный TEST — <https://test.ops.dzap.pw>; [app.dzap.pw](https://app.dzap.pw) остаётся заглушкой до принятого PROD. Обновление на Sigma делает назначенный оператор по [PIPELINE](../deploy/PIPELINE.md) для **точного** candidate: release archive, каталог, модель, mapping, recommendation override и policy. PROD credentials/uploads/feedback отделены от TEST. Не копировать окружение целиком, не запускать третью модель вслепую. При первом откате вернуть прежний маршрут-заглушку, остановив только новый app; не стирать данные и не останавливать чужой vision. Читателю публичного клона не нужны и не предоставляются серверные `/srv`-пути или полномочия оператора.
