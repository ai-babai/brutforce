# База данных и быстрые тестовые среды

Статус: предложение, БД продукта не установлена этим изменением. Существующий Go API пока использует synthetic JSON catalog.

## Предлагаемый минимум

PostgreSQL как постоянный локальный сервис и Goose с SQL-миграциями для Go backend.
Сначала только зона Макса: постоянная база плюс временные базы с отдельными ограниченными ролями.
Структура схемы живёт в apps/api/migrations/ после начала реализации. Прикладной процесс не superuser.
Каталог/связи/receipts — в БД; фотографии и веса — отдельно. Redis/векторная БД не обязательны.

## Что означает «быстро»

Не устанавливать PostgreSQL и не загружать весь датасет на каждом тесте.
Обычный цикл поведения Go/Vitest вообще не запускает БД, если проверяемое свойство этого не требует.
DB integration создаёт небольшую временную БД, применяет миграции, загружает малый seed и вызывает настоящий PostgreSQL.
Одну такую БД использовать для набора тестов, а не запускать сервер на каждый test case; изоляция тестов транзакциями
подходит только там, где проверяемый код использует управляемое тестом соединение. Для HTTP/нескольких соединений
нужна явная стратегия очистки/отдельных баз; внешний rollback не откатывает независимые соединения приложения.

Изменение одного .sql не требует пересборки PostgreSQL. Пересобирается только изменённый код приложения.
Крупный каталог импортировать отдельным этапом; не включать его в каждый короткий прогон.
При доказанной медлительности bootstrap можно клонировать закрытую seed-template по версии схемы/seed.
Template должен быть без активных подключений; это не копия живого datadir. Новая миграция должна проверяться
и с нуля, и как upgrade старой версии: шаблон не должен скрывать поломку последовательности миграций.

## Честный бюджет

Точного обещания в секундах пока нет: надо замерить cold/warm отдельно на Sigma.
Ориентир для первой реализации: bootstrap маленькой временной БД — единицы секунд,
DB-набор — десятки секунд, а не полный rebuild на каждую правку. Это цель, не результат теста.
Измерять отдельно создание, миграции, seed, тесты и полную сборку приложения.
Не ускорять ценой замены PostgreSQL на SQLite или исключения важной проверки.

## Сохранность

Рабочая lct_maks не disposable: пользовательские фото/данные нельзя сбрасывать автоматически.
Удаляется только явно запрошенная временная среда с проверенной регистрацией/владельцем.
Далее stage/prod имеют свои базы и роли. Уже применённые миграции не редактируются задним числом.
Откат приложения работает только при совместимой схеме; down не восстанавливает потерянные данные.
До production проверить восстановление backup. Инструкции и реальные команды дописать в том же PR, что реализацию.
