# Формат инструкций и развитие структуры

Согласовано Максом 2026-09-20: ограниченные входные инструкции и развивающаяся карта проекта.
Численные пределы выбраны для короткого читаемого входа:

- Не более **200 строк** в каждом поддерживаемом проектом AGENTS.md или CLAUDE.md.
- Не более **160 Unicode-символов на строку**, включая пробелы, и **12 000 символов на файл**, включая переводы строк.
- Эти пределы действуют для наших входных файлов, не для vendored/generated материалов и исторических снимков.
- Формат не заменяет смысл: одно правило на пункт, без плотных многострочных перечней в одной строке.
- Подробные процедуры, основания и примеры — в обычных тематических .md; в AGENTS остаются действие и короткая ссылка.
- Нельзя обходить лимит фиктивными AGENTS по пустым зонам. Локальный AGENTS нужен только для действительной области ответственности.

## Один источник каждого правила

MAP.md направляет в зону. STRUCTURE.md описывает существующие папки и их статус.
RULES.md — совместная работа; deploy/README.md — выпуск; DATABASE.md — БД; contracts — границы модулей.
OPERATING-RULES.md сохраняет подробные разрешения и правила из прежнего корневого AGENTS.
Не копируй эти документы в новые runbook с другими названиями. Ссылка лучше второй ручной версии.

## Изменения по мере использования

Изменил назначение папки, команду запуска, контракт или порядок выпуска — обнови карту/документ в том же PR.
В описании изменения укажи реальную причину неудобства и что стало проще. Новая папка не обязательна.
Объединение/разделение документов допустимо, если обновлены входящие ссылки и не потеряны ограничения.
Не удаляй прошлые отчёты/постоянные данные под видом уборки структуры. Не принимаемые ещё решения помечай предложением.
Не создавать RFC/ADR на каждое перемещение абзаца; отдельное решение нужно при существенном изменении обязанностей/поведения.

## Проверка

Перед push: проверить число строк/символов, относительные ссылки и соответствие фактическим папкам.
Для этой документационной правки достаточно разовой проверки, отдельный CI/framework не требуется.
После интеграции можно включить ту же проверку в существующий общий check, если это будет полезно.
