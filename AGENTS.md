# Контракт агентской работы Vino

Этот файл действует для основного проекта Vino в репозитории BrutForce.
Репозиторий, общая доска и серверные каталоги координируются по дополнительным
правилам в конце файла.

## Перед работой

1. Прочитай `INDEX.md` и `PROJECT.md`.
2. Прочитай `agents-os/BOOTSTRAP.md` и `agents-os/memory/WORKING.md`.
3. Найди назначенную задачу в `TASKS.md` и назови границу файлов, критерий
   результата и способ проверки.
4. Проверь `ERRORS.md` точным поиском по сущностям задачи.
5. Открой только относящиеся к задаче документы, профиль роли и исходные данные.

Не сканируй всё дерево данных и не загружай бинарные наборы без необходимости:
сначала используй манифесты, индексы и выборочные проверки.

## Правила продукта и данных

- Главный критерий — достоверный поиск конкретного вина по фотографии этикетки,
  особенно среди почти одинаковых позиций. Красивый интерфейс не компенсирует
  ошибочный `slug`.
- CV-поиск по изображению обязателен. OCR и метаданные могут усиливать решение,
  но не заменяют визуальный поиск.
- Отделяй требование, проверенный факт, гипотезу, экспериментальный результат и
  принятое решение.
- Не фиксируй стек из ТЗ как обязательный: Nuxt, PostgreSQL/pgvector, SigLIP 2,
  Strapi и Docker — рекомендуемый ориентир до сравнительного прототипа и ADR.
- Публичный benchmark, закрытый benchmark кейсодержателя, каталог и обучающие
  данные — разные контуры. Не используй test/private изображения для обучения,
  настройки порога, индекса или ручного подбора правил.
- Разбиение выполняй по идентичности товара и семейству похожих этикеток, а не
  случайно по изображениям. Дубликаты и производные одного фото не пересекают
  train/validation/test.
- Каждый объект данных получает происхождение, права использования, хеш,
  стабильный идентификатор, catalog membership и статус качества. `slug`
  обязателен только для подтверждённой связи со snapshot «Своё Вино»;
  российское вино без такой связи сохраняй как open-world reference.
  Неподтверждённые лицензии или соответствия не маскируй как допустимые.
- Различай `wine_family_id`, точный `bottle_variant_id`, `label_design_id` и
  винтаж. Ребрендинг и новый год — полезные hard cases, а не автоматические
  дубликаты или повод присвоить ближайший `slug`.
- Нерешённые identity/origin задачи направляй в `needs_verification`, сцены без
  полного набора SKU/bbox — в `needs_annotation`; media физически не перемещай.
- Сырые и приватные данные, веса, индексы и секреты не попадают в Git. В Git
  хранятся схемы, манифесты без чувствительных полей и воспроизводимый код.
- Проект использует данные только для некоммерческого исследования. Этот режим
  не отменяет атрибуцию, `ND`/`SA`, ограничения распространения и права на
  исходные изображения; допустимость фиксируется по каждому источнику.
- Пользовательские изображения валидируются по формату, размеру и ресурсоёмкости;
  метаданные удаляются из производных копий. Не логируй содержимое изображений.

## Инженерия и оценка

- Работай маленькими проверяемыми вертикальными срезами.
- Сначала зафиксируй baseline, выборки, метрики и критерий успеха, затем меняй
  модель, preprocessing, индекс или reranker.
- Основные метрики: exact top-1 accuracy, top-5 recall, macro F1, покрытие при
  отказе, ошибки по группам near-duplicate и p50/p95/p99 latency. Не выдавай
  одну метрику за другую.
- Top-1 ответ допустим без экрана выбора только при откалиброванном пороге и
  достаточном отрыве от второго кандидата. Иначе сервис честно сообщает
  `not_found` либо использует отдельно утверждённый fallback-сценарий.
- Контракт кейсодержателя `{"slug":"wine-slug"}` должен оставаться плоским и
  стабильным; диагностические поля не добавляются в него самовольно.
- Unit/contract tests не зависят от сети и GPU. Live, GPU и performance-прогоны
  маркируются отдельно, сохраняют конфиг, версии данных, seed, ревизию кода и
  фактическое оборудование.
- Цель SLA — до 3 секунд, но непроведённый замер не объявляется успешным.
- Секреты, токены, закрытые ссылки и приватные строки не попадают в Markdown,
  Git, фикстуры или логи.

## Координация и завершение

- Специализированные профили находятся в `.codex/agents/*.toml`; делегирование
  выполняй только по явной просьбе пользователя или применимой инструкции.
- Параллельные исполнители не редактируют один файл. Исполнитель не принимает
  собственный результат: значимый срез требует независимого review/QA.
- Перед передачей используй `agents-os/protocols/HANDOFF.md`.
- Во время прохода обновляй только рабочую память. Долговременные записи
  продвигай по `agents-os/protocols/MEMORY-LIFECYCLE.md`.
- `WORKING.md` — сжатое состояние, а не хронологический лог: цель — до 150 строк,
  жёсткий предел — 250. Историю значимых проходов храни в `runs/`.
- Документацию для людей пиши по-русски; английский используй для точных имён,
  API-полей, команд и идентификаторов.
- «Готово» означает наблюдаемый результат, выполненные относящиеся проверки,
  перечисленное непроверенное и один ясный следующий шаг.

## Репозиторий BrutForce и сервер

- Канонический Git-репозиторий: `https://github.com/ai-babai/brutforce`.
  Рабочие ветки называй `codex/<краткое-название>`; не редактируй `main`
  напрямую и не переписывай чужую историю.
- Каноническая очередь команды — GitHub Project `ai-babai` №2. Перед задачей
  прочитай `docs/agent-guide/BOARD.md`, проверь дубликат и занятость, укажи
  инициатора, область, исполнителя/сессию и наблюдаемый критерий готовности.
- На сервере сначала прочитай `/srv/AGENTS.md` и `/srv/lct/AGENTS.md`, затем
  сверяй живое состояние с `docs/agent-guide/SERVER.md`. Живые инструкции
  сервера имеют приоритет над локальным snapshot.
- `/srv/lct/repo` — чистая основная копия, `/srv/lct/work` — отдельные worktree
  задач, `/srv/lct/data/{roman,maks,prod}` — данные вне Git. Не переносить в
  серверные команды локальные Windows/macOS-пути.
- Не отключай проверку SSH host key. Не печатай приватные ключи, токены,
  пароли или содержимое credential store. Переданные через чат ключи после
  использования подлежат ротации.
- Серверные `notes/activity` — вспомогательная запись со ссылкой на карточку,
  а не второй источник задач. GitHub deploy key сервера не даёт доступа к API
  Project.
