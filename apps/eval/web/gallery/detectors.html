Сравниваем выбор бутылки, визуальные признаки и поиск по тексту на одних корзинах и отдельно на реальных фотографиях организаторов.

Схемы решений

Что именно сравниваем

Детектор выделяет область изображения. Он ещё не знает, какая карточка каталога ей соответствует. За поиск карточки отвечают следующие ступени.

1. OWLv2 · исходный вариант

полный кадр
  |
OWLv2: бутылки
  |
SigLIP2: винная ли бутылка?
  |
центральный винный кандидат
  |
OWLv2: этикетка + контекст
  |
визуальный поиск + OCR

Два прохода OWLv2. Для отдельной этикетки есть запасной путь, когда бутылок не найдено. Это исходная композиция v2.

2. YOLOE-26s · два поиска по словам

полный кадр
  |
YOLOE: бутылки по 7 описаниям
  |
SigLIP2 + выбор винной цели
  |
YOLOE: этикетки по 3 описаниям
  |
этикетка + контекст
  |
визуальный поиск + OCR

Два экземпляра одних весов с разными заранее вычисленными текстовыми признаками. Маски не используются: сравниваем рамки. Проверяем также ошибочное принятие других предметов за вино.

3. YOLO26n · заменить только бутылку

полный кадр
  |
YOLO26n: класс bottle
  |
SigLIP2 + выбор винной цели
  |
OWLv2: этикетка + контекст
  |
визуальный поиск + OCR

Стандартный класс «бутылка» включает не только вино. Сохраняем проверку винной цели и прежний поиск этикетки, чтобы измерить эффект одной замены.

4. YOLO26n · этикетка по геометрии

полный кадр
  |
YOLO26n: класс bottle
  |
SigLIP2 + выбор винной цели
  |
фиксированная область:
6–94% ширины, 30–92% высоты
  |
визуальный поиск + OCR

Полностью убираем OWLv2 из обработки запроса. Это приблизительный фрагмент, а не обнаруженная этикетка. Отдельная этикетка без бутылки требует другого пути. Каталожный индекс остаётся v2: меняется только обработка запроса.

5. RT-DETR R18 · ещё один детектор бутылки

полный кадр
  |
RT-DETR R18: класс bottle
  |
SigLIP2 + выбор винной цели
  |
OWLv2: этикетка + контекст
  |
визуальный поиск + OCR

Ещё одна замена только первого детектора. Сохраняем дальнейшие шаги, чтобы сравнение не смешивало несколько изменений. Код и выбранные веса доступны под Apache 2.0.

6. RT-DETR + SO400M · сильная композиция

RT-DETR: бутылки
  |
Base-224: выбрать центральное вино
  |
цель целиком + OWLv2: этикетка
  |
SO400M: два визуальных вектора
  |
кандидаты по фото + PaddleOCR
  |
объединение → slug

Меняется энкодер поиска; классификатор винной цели остаётся Base. Упрощённая ветвь использует только изображение цели: после выбора бутылки пропускает обычный поиск этикетки и OCR. Запасной путь отдельной этикетки сохранён.

Общая схема поиска после выбора цели

                выбранная цель
        +-------------+-------------+
        |             |             |
   SigLIP2:      SigLIP2:       PaddleOCR:
   цель целиком  этикетка       прочитать текст
        |             |             |
   близость к    близость к    поиск слов
   фото каталога этикеткам     во всём каталоге
        |             |             |
        +-------------+-------------+
                      |
           объединение списков (RRF)
                      |
               slug карточки

Один визуальный энкодер — Base-224 в первом опыте или SO400M-384 в новой композиции — обрабатывает два разных фрагмента. Каталожные векторы рассчитаны заранее. OCR добавляет собственных кандидатов. Сначала оцениваем каждую ветвь отдельно, затем пары и все три; веса 25/35/40% фиксированы, обучения нет. RRF даёт карточке тем больше баллов, чем выше её место в каждом списке.

Service и retrieval разделены. Полный кадр проходит выбор центрального вина. В поисковой корзине уже дан кроп: поиск бутылки пропускается. «Цель целиком» здесь означает весь переданный кроп. Результаты этих двух режимов нельзя складывать в одну точность.

Отдельные проверки эмбеддинга. SO400M-384 заменяет Base-224 при сохранённых фрагментах, OCR и правилах объединения. В опыте с чёрно-белым изображением меняем только цвет этикетки одновременно у запроса и каталога. Эти пересчёты рангов показывают вклад признаков; они не выдают себя за измеренный полный HTTP-сервис.

Как устроены отдельные текстовые бейзлайны
полный кадр
  |
DeepSeek V4.1 Flash / Qwen3.8-27B
выбрать центральное вино,
прочитать только видимые надписи
  |
производитель, название, сорт,
год и дословный текст
  |
обычный поиск по строкам каталога
  |
ранжированный список slug

Два независимых API-бейзлайна. Языковой модели не дают правильный slug: она возвращает текст. Затем одинаковый код сравнивает буквенные тройки и слова с названиями и производителями всех 2103 карточек. Это и называлось «матчером» в прежнем отчёте. PaddleOCR-бейзлайн использует тот же поиск по каталогу, но читает текст мобильным OCR с геометрическим центральным фрагментом; отдельного визуального эмбеддинга у него нет.

Воспроизводимость

Прогоны добавляются в общую матрицу. Инструкция для агентов объясняет получение корзин и отправку результатов. Прежние измерения сохранены в первом отчёте.

Локально проверенная разметка не является официальным ключом организаторов. Закрытые ответы и исходные журналы хранятся отдельно.
