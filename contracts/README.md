# Контракты

Пока фиксируем процесс, а не неподтверждённую схему данных.

Перед реализацией каждой самостоятельной границы описываем:

1. Назначение, производитель и потребители.
2. Входы: обязательные поля, типы, единицы и ограничения.
3. Выходы: идентификаторы, смысл результата, порядок кандидатов.
4. Ошибки и неоднозначность: неверный файл, отсутствие кандидатов, сбой поиска.
5. Правила хранения данных и совместимости.
6. Способ проверки наблюдаемого поведения; ограничения тестовой политики из AGENTS.md сохраняются.

Для текущей границы добавляй короткий пример «вход/условие → ожидаемый наблюдаемый результат» со ссылкой на подтверждённое требование. Формат JSON сам по себе не доказывает правильное поведение. Не требуется отдельный BDD-фреймворк или документ на каждый сценарий.

Предполагаемые границы для обсуждения:

- Импорт каталога → внутренняя запись вина и изображения.
- Клиент → API поиска по фотографии.
- Поиск → ранжированные идентификаторы каталога и диагностические сигналы.
- Оценка → зафиксированная версия каталога, запросов, метода и метрик.

Конкретные схемы появятся после проверки ТЗ и данных. Если выберем FastAPI, один из вариантов — Python-схемы как источник истины, из которых экспортируется OpenAPI и генерируются клиентские типы. JSON Schema/OpenAPI вручную одновременно с независимыми Python-типами не ведём.

Число сходства не называется вероятностью правильного ответа без калибровки. Отказ от ответа или top-k согласуются с конкурсной метрикой.
